# Фактически работающая интеграция

Дата исходного контракта: 2026-09-19. Версия API: v1. Это временный внутренний контракт **синтетического примера**, не схема организаторов.

> Каждый участник обновляет свой раздел `INTEGRATION.md` в том же PR, где меняет интерфейс, формат данных, конфигурацию или способ запуска. Перед несовместимым изменением он согласует его с владельцем принимающей части. Запланированное изменение не отмечается как уже реализованное.

## Общие договорённости — Даниэль

Поток данных: константный синтетический пример → `ml.forecast.predict_mock()` через `ml.adapter.predict_for_api_v1()` с проверкой версии → FastAPI → HTTP `/api` через прокси frontend → React-график и таблица.
ML вызывается как Python-модуль в процессе backend; отдельного ML-сервиса нет.

| Компонент | Владелец | Адрес / порт |
|---|---|---|
| Frontend | Артём | http://localhost:5173 |
| Backend | Толя | http://localhost:8000 |
| ML, признаки, качество | Георгий | Python-модуль, без порта |
| ML-интерфейс, архитектура | Даниэль | Согласование контракта |
| Данные, интеграционные проверки | Игорь | Локальные файлы, без порта |

Команды из корня: `.venv/bin/python -m uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000`; в отдельном терминале `npm --prefix frontend run dev`.
Установка окружения описана в README. Контейнеры: `docker compose up --build`, остановка: `docker compose down`.
Не запускайте локальные процессы и Compose одновременно на одинаковых портах.

Переменная `BACKEND_URL` задаёт **серверный** адрес прокси Vite; по умолчанию `http://127.0.0.1:8000`, в Compose — `http://backend:8000`.
Для локального запуска читается `.env` из корня; переменная процесса имеет приоритет. После изменения перезапустите frontend.
Браузер запрашивает относительный `/api/v1/...` на порту 5173 и никогда не обращается к имени `backend`. CORS не требуется при этом сценарии.
В контейнере backend есть обе директории `backend/` и `ml/`, рабочая директория `/app` обеспечивает импорт.

## Frontend — Артём

React + TypeScript + Vite; одна страница. При загрузке и по кнопке сначала проверяется health, затем запрашивается прогноз. Общий таймаут — 10 секунд.
Есть загрузка, сообщение о неудаче, повтор запроса и явная маркировка тестовых данных. При повторе старый график удаляется, чтобы не выдавать его за свежий ответ.
График и доступная таблица используют только ответ API. Времена показываются с исходным смещением, без преобразования в часовой пояс браузера.
`npm --prefix frontend run build` проверяет TypeScript и собирает `frontend/dist/`.
Над графиком расположена схема трамваев Москвы (`TramMap`), которую приложение рисует само по геометрии линий (`network.json`): pan/zoom, клик по линии выделяет её, без обращений к API и без связи с прогнозом. Схема строится из локального PDF скриптом `scripts/map/extract_lanes.py` в `frontend/public/map-local/`; готовый `network.json` теперь поставляется через Git, а отсутствие полной карты останавливает сборку. На схеме отрисованы точки остановок и подписи (в том числе под углом; тексты получены OCR из PDF скриптом `scripts/map/build_stops.py`, часть поправлена вручную; возможны ошибки). Также нарисованы иллюстрации достопримечательностей и значки метро/МЦК из PDF (`scripts/map/build_icons.py`). Клик по остановке и выбор маршрута целиком — **запланировано, не реализовано**; привязка к прогнозу потребует расширения API и согласования с Толей.
Compose собирает frontend и запускает Vite preview; это средство локальной проверки, не схема production-развёртывания.

## Backend — Толя

Авторитетная автоматически генерируемая схема: [Swagger UI](http://localhost:8000/docs), [OpenAPI JSON](http://localhost:8000/openapi.json).
Ниже — примеры текущего контракта; ручное описание API в других документах не дублируется.

```sh
curl http://localhost:8000/api/v1/health
```

HTTP 200:

```json
{"status":"ok"}
```

Health подтверждает доступность API, не качество модели и не наличие данных организаторов.

```sh
curl http://localhost:8000/api/v1/forecast
```

HTTP 200:

```json
{
  "is_mock": true,
  "unit": "passengers",
  "points": [
    {"timestamp": "2026-01-01T09:00:00+03:00", "value": 12},
    {"timestamp": "2026-01-01T09:15:00+03:00", "value": 18},
    {"timestamp": "2026-01-01T09:30:00+03:00", "value": 15},
    {"timestamp": "2026-01-01T09:45:00+03:00", "value": 24},
    {"timestamp": "2026-01-01T10:00:00+03:00", "value": 21},
    {"timestamp": "2026-01-01T10:15:00+03:00", "value": 16}
  ]
}
```

`is_mock: true` обязателен; `unit: passengers` — условное количество пассажиров, `value` — целое неотрицательное число. Это иллюстративная величина без привязки к остановке, маршруту или фактической агрегации.
`timestamp` — ISO 8601 с обязательным часовым смещением; текущие точки используют `+03:00`, расположены по времени через 15 минут. Эти интервалы не задают будущий горизонт задачи.
Список `points` непустой. Backend проверяет структуру результата через Pydantic.
Если ML-функция бросает исключение или возвращает некорректный результат: HTTP 503, `{"detail":"Forecast temporarily unavailable"}`; подробности пишутся в серверный журнал.
Фильтров и параметров запроса нет.

## ML — Георгий; интерфейс — Даниэль

`from ml.forecast import predict_mock`, затем `predict_mock() -> dict`.
Этот публичный интерфейс сохранён. Backend вызывает его через `ml.adapter.predict_for_api_v1()`: перед inference проверяется `ml.forecast.CONTRACT_VERSION == "synthetic-v1"`. Неизвестная или отсутствующая версия вызывает `IncompatibleForecastContract` и прежний HTTP 503; провайдер не запускается. Pydantic по-прежнему проверяет результат. Это проверка совместимости только синтетического контракта, не loader реальной модели/manifest и не готовность данных. Форма HTTP-ответа и OpenAPI v1 не изменены.
Входов нет; функция не читает файлы, сеть, текущее время и не использует случайность.
Выход — новый словарь точно в формате примера выше. Каждый вызов возвращает одинаковые значения; изменение одного результата не влияет на следующий.
Штатных ошибок нет. Неожиданное исключение передаётся backend, который отвечает 503. Обработку будущих ошибок реальной модели предстоит согласовать отдельно.
Вся ML-логика сейчас — **тестовая заглушка**, обучение и оценка качества отсутствуют.

## Data и интеграционные проверки — Игорь

Реальных данных нет. Единственный синтетический пример задаётся внутри ML-модуля.
Реальные файлы храните локально в `data/`: содержимое по умолчанию исключено из Git. Перед добавлением любых материалов проверьте правила организаторов; `.gitignore` не заменяет проверку.
Не определены формат датасета, протокол эмулятора и формат файла для автоматической проверки.
Проверки: `.venv/bin/python -m unittest discover -s tests/integration -v`. Они проверяют детерминированность, вызов ML через API, контракт времени/единиц и ответ при сбое ML.
Ручная проверка браузера: загрузка графика, остановка backend, повтор запроса и сообщение об ошибке, восстановление после запуска backend.

## Автоматические проверки — Игорь и Даниэль

`.github/workflows/ci.yml` запускается на каждый push в любую ветку, на открытие/обновление PR и вручную (`workflow_dispatch`). На Ubuntu 24.04 независимо выполняются:

- backend: Python 3.12, установка `backend/requirements.txt`, `pip check`, 9 интеграционных тестов, включая отказ до inference при несовместимой/отсутствующей версии;
- frontend: Node.js 22.16.0, `npm ci --prefix frontend`, `npm run build --prefix frontend`;
- Compose: проверка конфигурации, сборка и запуск контейнеров, HTTP-проверка страницы и API через прокси на порту 5173. Результат контейнерного API сравнивается с ML-модулем из текущего checkout.

При сбое Compose журнал контейнеров выводится в Actions; контейнеры всегда останавливаются. Доступ workflow к репозиторию — только чтение, секретов и публикации нет. Новый запуск на той же ветке отменяет устаревший.
Это проверка программной связки, не качества ML. Автоматических браузерных тестов нет. При смене контракта или команд запуска обновляйте workflow вместе с этим документом.

Общая команда smoke после запуска frontend/backend: `.venv/bin/python -m scripts.check_integration --base-url http://127.0.0.1:5173`. Она проверяет HTML, health и точное совпадение прогноза через frontend-прокси с ML текущего checkout; при ошибке завершается ненулевым кодом. В Compose job CI вызывается та же команда через `python3`. Проверка не запускает сервисы и не подтверждает готовность реальной модели.

## Единая доставка карты и серверное обновление — 2026-09-25

Подготовлено локально: Git разрешает включать готовый
`frontend/public/map-local/network.json`; PDF, OCR-промежуточные файлы, датасеты,
веса и секреты остаются исключёнными. Автор карты обновляет итоговый JSON в том же
PR, что и интерфейс. Получатели скачивают готовую карту обычным `git pull`,
без Python/OCR. HTTP API и формат карты не изменены.

`npm run build` через `prebuild` проверяет комплектацию карты: viewBox, линии,
остановки, подписи, легенду, достопримечательности и метро. Неполная карта останавливает
сборку и CI. Это проверка комплектации, не точности распознавания.
`deploy/update.sh` собирает и проверяет карту, обновляет backend и статику,
сохраняет предыдущие версии и сверяет опубликованный HTML/JSON.
После доставки этих файлов и карты в main команда VPS из `/opt/tramflow`:
`git pull --ff-only origin main && bash deploy/update.sh`.

в frontend/public/map-local/: 45 линий, 1098 точек остановок, 424 подписи,
47 достопримечательностей, 58 значков метро и 36 записей легенды. Это числа
элементов схемы, не уникальных транспортных объектов. Проверка комплектации пройдена.

**Проверено локально:** комплектация карты, сборка актуального frontend и совпадение JSON
в dist с исходным файлом. Серверный запуск нового скрипта не проверен;
