### Этап B. Надёжность демонстрации

Приоритет — воспроизводимый запуск и совпадение данных по всему пути:

- совместимый ML ZIP импортируется в новый каталог и проходит проверку;
- ready → capabilities → query работает через тот же proxy, что использует UI;
- день, неделя и месяц используют поддержанный диапазон пакета и МСК;
- batch/API/график/таблица/CSV согласованы; экспорт закреплён на run/result;
- проверены смена фильтра, отсутствие пакета, остановка и восстановление backend,
  устаревший run, несовпадение результата, partial/null/no_data;
- № 5 обозначен нулевым baseline, без ложного объяснения отсутствием движения;
- карта сохраняет работоспособность; неподтверждённые остановки/линии не получают
  выдуманный прогноз и неверную привязку маршрута;
- чистая поставка содержит исходники и готовую карту, а документация объясняет
  отдельное получение разрешённых локальных ML-артефактов.

   в том же наборе изменений. Проверь diff и выполни затронутые проверки.
3. Передай точную проверяемую версию Claude. Занеси находки в журнал:
   ID → приоритет → принято/опровергнуто/зависит от владельца → доказательство.
4. Воспроизведи и исправь обоснованные замечания. Не выполняй совет вслепую:
   факты репозитория, требования и ограничения важнее мнения ревьюера.
   Спорное замечание обсуди с Claude через конкретный контрпример/проверку.
5. Повтори затронутые проверки и отправь исправления на повторное ревью.
   После двух безрезультатных кругов пересмотри гипотезу; не спорь бесконечно
   и не закрывай критический дефект ради формального завершения.
6. Сохрани законченный этап отдельным коммитом, отправь свою ветку, создай или
   обнови PR. Частичный результат можно отправить как явно незавершённый draft.
7. Дождись CI именно на текущем head SHA. Исправь относящиеся к изменению сбои;
   не удаляй проверки и не понижай требования, чтобы получить зелёный статус.
8. Сливай только при закрытых подтверждённых P0/P1 по объёму PR, полученном ревью
   Claude, применимых зелёных CI и соблюдённых правилах GitHub. Не обходи required
   approvals. Самоодобрение PR через Claude не является GitHub review владельца.
9. Если main изменился, совмести изменения в своей ветке без переписывания чужой
   истории, повтори затронутые проверки и ревью новых конфликтов/поведения.
   Перед слиянием повторно проверь актуальность SHA и CI. После слияния проверь
   итоговую ветку; публикация GitHub сама по себе не подтверждает обновление VPS.

Вмешательство в готовый PR Артёма допустимо только для явно переданной интеграции
и в собственной ветке. Не меняй его исходную рабочую ветку. Остальные чужие PR
не сливай в рамках общего разрешения этого ТЗ.

При создании PR укажи проблему, результат, проверки, ограничения и связь с
требованием; прикрепи ссылку к задаче средствами приложения, если они доступны.
Обзорный итог ревью можно включить в собственный PR. Не рассылай сообщения
команде, организаторам, в почту или мессенджеры.

## 9. Проверки

Уточняй актуальные команды в README частей и workflows. Используй Python 3.12,
локальные зависимости и lock-файлы. Базовый набор проекта:

```sh
python -m pip check
python -m unittest discover -s backend/tests -v
python -m backend.contracts.openapi --check
python -m unittest discover -s tests/integration -v
python -m unittest discover -s tests/ml -v
python -m unittest discover -s tests/tooling -v
python -m scripts.check_delivery
npm ci --prefix frontend
npm --prefix frontend run build
docker compose config --quiet
NODE_PATH="$PWD/frontend/node_modules" QA_BROWSER=chromium python tests/frontend/run_browser.py
```

Команды запускаются в подготовленном окружении соответствующей рабочей копии.
Для браузера установи требуемый runtime по frontend/README.md. check_delivery
проверяет состав Git: не обходи его ошибку неучтённого файла удалением нужного
исходника; включи только собственные проверенные файлы в правильную поставку.
Для реального пакета отдельно выполни backend.handoff.check и браузерный проход
с QA_RELEASE по документированному сценарию. Подними Compose и проверь сервисы:
одного config --quiet или frontend build для этого недостаточно.

На промежуточных исправлениях запускай подходящие проверки. Полный применимый
набор выполни на итоговой версии. Не повторяй дорогое обучение и нагрузку без
изменений или новой причины. Используй отдельные порты и имя Compose-проекта;
останавливай только собственные процессы и контейнеры.

## 10. Продолжения цели, журнал и блокировки

Не заканчивай работу после составления плана или первого ревью, если остаются
доступные пункты цели. При продолжении читай журнал, проверяй актуальные файлы
и возвращайся к следующему незавершённому шагу; не начинай аудит сначала.

Веди локально в игнорируемом artifacts/night-review/<run-id>/:

- state.md: согласованный объём, срок, репозиторий, рабочая копия, HEAD,
  завершённые этапы, следующий шаг и открытые зависимости;
- reviews/: реальные запросы/ответы Claude и статус каждой находки;
- checks/: команды, версии, результаты и безопасные доказательства.

Общедоступный итог без закрытых материалов сохрани в
docs/verification-night-<дата>.md. Новые отчёты и артефакты не должны затирать
существующие. Перед окончанием каждого существенного этапа обновляй журнал.

Если Claude, GitHub, CI, Docker или нужный артефакт недоступен, зафиксируй
точную ошибку и последствия. Допустимы ограниченные повторы временного сбоя;
не обходи квоты и не запускай бесконечный опрос. Пока идёт ожидание, делай
независимую работу. Без Claude можно подготовить и проверить draft, но нельзя
утверждать, что внешнее ревью пройдено, или сливать его по правилам этого ТЗ.

Неподтверждённый контракт, недоступная карта или чужая текущая ML-задача блокируют
зависимую часть, а не всю полезную работу. Не проси спящего пользователя решить
обычные технические вопросы. Необходимое новое разрешение не заменяй таймаутом.
Статусы цели complete/blocked/paused используй по правилам инструментов:
не ставь complete из-за окончания времени и paused без просьбы пользователя.

По умолчанию ночное окно — восемь часов от согласия. Бюджет цели и более ранний
срок пользователя имеют приоритет. Оставь последние 45 минут на итоговые
проверки, сохранение работы и отчёт. До этого момента приоритет имеют задачи,
которые реально можно завершить. Не увеличивай бюджет, не покупай вычисления,
не создавай самовозобновляющиеся процессы и не расходуй reset-кредиты сам.
Работа не должна продолжаться бесконечно ради формулировки «победить».

## 11. Критерии завершения и утренний результат

Цель достигнута, когда:

- матрица требований актуальна; обязательные для согласованного объёма пункты
  закрыты доказательствами, допустимые ограничения обоснованы источниками;
- итоговая версия воспроизводимо запускается и проходит применимые проверки;
- доступный реальный прогноз согласован между batch, API, UI и CSV;
- готовая переданная карта Артёма интегрирована и проверена; если она ещё не
  передана, зависимый пункт остаётся открытым, а не считается выполненным;
- Claude проверил финальную версию и закрытие подтверждённых P0/P1; его ответ
  сохранён, оставшиеся P2 оценены и не мешают согласованному результату;
- законченные изменения опубликованы, CI проверен; разрешённые слияния выполнены
  либо явно указано внешнее ограничение, из-за которого публикация не завершена;
- материалы защиты и поставки соответствуют реализованной версии; лицензия,
  действующие контракты и работа команды сохранены.

Если обязательный пункт открыт, результат — частично подготовленная версия с
конкретным блокером; не помечай цель успешно выполненной. Исчерпание срока или
бюджета не доказывает достижение цели. Сохрани доступный результат и честный статус.

Утренний ответ должен содержать:

1. Что улучшено и какой критерий/сценарий это закрывает.
2. Ссылки на PR, commit и CI; что слито, что осталось в draft.
3. Основные замечания Claude и доказательства исправлений.
4. Какие проверки пройдены именно этой версией; известные ограничения.
5. Состояние карты Артёма, модели и локальных комплектов; точную команду запуска.
6. Что требует решения Даниэля, в порядке важности; отдельно статус VPS и
   конкурсной отправки, которые данным ТЗ не разрешены.
