score платформы >0,88, связанный с точным CSV, и модель, воспроизводящая этот CSV.
Локальное значение >0,88 не заменяет платформенную оценку.

### DF-05c. Дополнительные категории внешних данных

Проверять отдельно погоду, дорожный трафик и прочие факторы. Календарь/сезонность
образуют одну категорию; несколько API одной категории не дают несколько баллов.
Начать с уже полученных материалов и журналов: прежний отрицательный погодный
опыт не повторять без новой проверяемой причины.

На каждую категорию подготовить цепочку:
`источник/ссылка → период и время доступности → snapshot/hash → join → признаки
→ сравнение с контролем → решение о включении → зависимость итогового артефакта`.

Источник должен реально участвовать в принятом прогнозе и иметь подтверждённый
эффект. Проверить пропуски, географическое/временное покрытие и отсутствие
размножения строк при join. Operational-доступность на origin и разрешённый
конкурсный ретро-режим описывать раздельно; ERA5-реанализ не называть архивным
прогнозом погоды. Не добавлять вредный фактор ради галочки и не компенсировать
отсутствие абляции ручным коэффициентом в UI.

**Приёмка:** в `ml/external-sources.json` и A2 для каждой категории указан
один из фактических статусов: включена с доказательством эффекта, проверена и
отклонена, отсутствуют данные. Новые данные/веса/OOF остаются вне Git.
Отказ от источника — допустимый результат работы, но не заработанный балл.

## 9. DF-06 — остановки и участки

**Известная зависимость:** [аудит данных](../../ml/reports/data-audit.md) указывает,
что справочник покрывает только часть маршрутов и сам не создаёт остановочный
target. Схема 2026 не подтверждает топологию истории 2025.

### Этап A. Проверить возможность расчёта

1. По официальному описанию и фактическим файлам проверить наличие связи
   успешной валидации с остановкой либо достаточной телематикой/расписанием
   для обоснованного сопоставления. Не выводить такую связь только из номера
   маршрута, устройства, гаражного номера или пикселей схемы.
2. Зафиксировать семантику stop/segment/direction, единицу, интервалы действия
   справочника, timezone, ключи join, покрытие маршрутов/периодов, долю
   неоднозначных и непривязанных событий. Проверить, что join не создаёт дубли.
3. Если входов нет, подготовить конкретный запрос недостающих данных:
   идентификатор остановки на событии либо нужная телематика, историческая
   топология и правила сопоставления. Не придумывать формат организаторов.
   Статус функции — `blocked_missing_data`; критерий остаётся незакрытым.

### Этап B. Реализовать при достаточных входах

1. Зафиксировать с владельцами совместимый дополнительный контракт: ID,
   зерно, единицы, доступные маршруты, пропуски, coverage и суммирование.
   Route-hour B2 и конкурсный DS сохраняют прежнюю семантику.
2. Реализовать воспроизводимую сборку stop-hour target и временную оценку
   остановочного прогноза. Выделить все непривязанные события; проверять баланс
   `привязанные + непривязанные = исходный target` для одинакового scope.
   Если выбран только участок, отдельно определить физический смысл величины:
   посадки на остановках участка не равны пассажирам внутри вагонов на участке.
3. Добавить выбор остановки/участка, динамику по времени, географическую
   привязку, API и CSV того же результата. Неподдерживаемые маршруты и даты
   должны явно показывать отсутствие этой детализации.
4. Проверить raw → target → прогноз → API → карта/таблица → CSV на первой
   и последней доступных датах, пропусках, неизвестном stop_id и смене фильтров.

**Приёмка функции:** подтверждённое происхождение остановочных значений,
временная оценка качества, сохранение баланса и воспроизводимая доставка.
Равное деление route total по остановкам, повтор одного route total у каждой
остановки или подсветка линии не считаются остановочным прогнозом.
Частичное подтверждённое покрытие указывать явно; оно не означает покрытие всех маршрутов.

## 10. DF-07 — итоговая приёмка

Для каждой задачи записать: статус, commit/снимок, изменённые части, доказательства,
команду повторения, ограничения и влияние на критерий. Статусы реализации:
`done`, `partial`, `blocked_missing_data`, `no_improvement`, `not_started`.
Для доставки отдельно: `ready_for_submission`, `submitted`. Не ставить общий
«всё закрыто», если DF-05 не достиг порога или DF-06 остался без данных.

Проверки выбирать по изменениям:

- Документы: ссылки, согласованность статусов, инструкции и состав source bundle.
- UI/API: build, затронутые backend/integration/browser проверки; день/месяц,
  год, коэффициенты/reset, № 5, unsupported, partial/null, ошибки и pinned CSV;
  desktop/mobile. Не писать тесты, которые лишь повторяют текст документации.
- Новый ML/data: временные срезы, отсутствие утечек, исходные ключи/балансы,
  повторяемый inference и полная цепочка до экспорта.
- Новый путь расчёта/состав ответа: измерить его отдельно в описанном профиле
  CPU/RAM. Не выдавать прежние 200 RPS за производительность нового endpoint,
  ML inference или VPS. Если путь не менялся, приложить прежние доказательства
  с точной версией и обоснованием применимости.
- Окончательная поставка: новый архив/manifests, clean launch, сверка версии
  модели и прогноза, инструкции доступа и сохранение run после restart.

Рабочие команды и профиль проверок брать из актуальных README и протоколов,
а не из устаревшего числа тестов. `scripts.check_delivery` требует включения
новых файлов в Git; до отдельного разрешения на Git-действия явно отражать
untracked-файлы, проверять локальные ссылки и explicit allowlist без обхода контроля.
