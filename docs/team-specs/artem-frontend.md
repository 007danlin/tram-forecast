# Артём: интерфейс диспетчера

Зона ответственности: `frontend/`. Результат - рабочий диспетчерский экран на существующем React/TypeScript/Vite, использующий реальный API. Основа: [общий контракт](shared-contract.md) и [сценарии/дизайн](dispatcher-ux.md). Принимают Даниэль и Игорь.

## Что получить до реализации интеграции

- От Толи: OpenAPI/типы, URL, синтетические ответы model/baseline/synthetic/qualitative, empty, partial, stale, error; ограничения и правила версий.
- От Игоря: справочники, геометрия и карта соответствий PDF-схемы, если она применяется. Каждое соответствие имеет статус проверки.
- От Георгия через backend: единица, reference_value, priority, состав использованных факторов и интервалы, если они действительно проверены.
- От Даниэля: принятый состав первого экрана, обязательный сценарий демо и решение спорных терминов.

Пока реальный API не готов, работать на общих синтетических fixtures. Не придумывать отдельный формат frontend. Mock-режим включается явно и визуально обозначается. Нельзя подставлять существующие шесть общих точек v1 под выбранный реальный маршрут.

## Техническое поведение

Один источник состояния фильтров и выбранного результата. При изменении запроса отменять старый через AbortController и проверять актуальность ответа; более медленный ответ на предыдущий маршрут не перерисовывает новый. Поиск и коэффициенты отправляются с debounce около 300 мс либо по «Применить». Ошибки отмены запроса не показываются как авария.

Переключение времени в пределах загруженного среза выполняется локально, без полного запроса на каждый шаг. Смена версии прогноза применяется атомарно. Ручное обновление запрашивает актуальный run; экспорт закрепляет отображённый. Фоновое обновление не меняет фильтры и выбранный объект.

Показывать время расчёта и время последних фактов. Баннер synthetic/историческое воспроизведение нельзя спрятать в tooltip. Список факторов различает «использован», «недоступен», «только сценарий». Информация о модели и подробные версии доступны через вторичный блок, не загромождают основную работу.

Карта при недоступной подложке оставляет список/таблицу/прогноз рабочими. Ресурсы исходной PDF-схемы готовятся по отдельному ТЗ и не публикуются автоматически. Цвет выбранного маршрута и цвет уровня спроса должны различаться по роли.

Предлагаемая декомпозиция: `api/`, `types/`, `components/Filters`, `TramMap`, `ForecastChart`, `ForecastTable`, `RouteDetails`, `ScenarioPanel`, `DataStatus`. Имена можно адаптировать, смысл границ сохранить. Новые зависимости добавлять по реальной необходимости.

## Что передать команде

Рабочую страницу, перечень UI-состояний и инструкцию ручной проверки; обновлённый frontend README; соответствующий раздел `INTEGRATION.md` после реализации; синтетические примеры спорных состояний. Скриншоты для отчёта не должны раскрывать запрещённые исходные данные.

## Приёмка Артёма

- `npm --prefix frontend run build` проходит.
- Два быстрых переключения маршрута не приводят к отображению первого ответа поверх второго.
- Выбор маршрута/направления/часа одинаков на карте, графике и таблице.
- Пять проверенных значений совпадают с API и CSV; единицы, дата и МСК видны.
- Сброс сценария возвращает базовые значения; изменение фильтра не оставляет старый коэффициент скрытым.
- При 503, отсутствии геометрии, partial и stale страница понятна и не показывает вымысел.
- Управление фильтрами/карточкой доступно с клавиатуры; фокус виден; цвет не единственный сигнал.
- Три коллеги выполняют задания проверки удобства; найденные блокирующие проблемы исправлены.

Не входит в задачу: собственная ML-логика, расчёт заполненности из оплат, изменение backend-контракта без Толи, новый отдельный веб-проект или переписывание приложения под другой стек.
