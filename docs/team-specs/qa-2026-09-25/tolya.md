# Дополнительное ТЗ Толе по API и расчётам

25 сентября 2026. Продолжение BE-01, BE-03, BE-04, BE-05 и BE-07. Принимают Даниэль, Артём и Игорь. API v2 пока остаётся проектом до согласования; источники Q&A указаны с локальным временем.

Дополнение уточняет область прогноза, недельную агрегацию, округление и исполнение долгих расчётов. Подготовь согласованный вариант схем и примеров раньше реализации, чтобы Артём мог продолжать интерфейс.

## P0 Область модели и конкурсный fallback

[Письменное уточнение](../../integration/qa-2026-09-25/submission-clarification.md) сохраняет № 5 в исходном sample. Нулевой fallback в конкурсном CSV не является основанием объявить маршрут обученной моделью или состоянием no_service. Не удаляй № 5 из справочников по прежней трактовке Q&A; получи от Игоря/Георгия фактическую область модели и методы расчёта.

Доступность API определяется принятым артефактом и capabilities. Если fallback поддержан продуктом, согласуй его явную маркировку. Для неподдержанного объекта используй принятую семантику ошибки; отсутствие данных не заменяется синтетическим успешным ответом. Общая карта может содержать больше маршрутов.

**Готово:** capabilities и методы выдачи согласованы с моделью; fallback и неподдержанный объект различимы для UI. Контракт API не меняется этим документом.

## P0 Неделя и дневная агрегация

Ответ задаёт сутки по часам, неделю и месяц по дням: **1.docx 11:20–12:01; 2.docx 01:00**. Добавь поддержку недельного просмотра в проект контракта. Если существующий запрос периода уже выражает семь дней с шагом день, используй его — отдельный endpoint не требуется.

Предлагаемая семантика команды: семь календарных суток начиная с выбранной даты в МСК, семь дневных интервалов [start, end). Согласуй её с Артёмом и Даниэлем. «Месяц = 30 дней» остаётся прежним внутренним решением, точный период должен быть виден.

Агрегируй совместимые часовые значения одного run и одного показателя. Пропуски отражаются в покрытии; неполная сумма не называется полным дневным итогом. ML не запускается заново ради переключения представления, если нужный run уже готов.

**Готово:** пример семи дневных строк, корректные границы МСК, одинаковые значения API/таблицы/диспетчерского CSV и тест частичного дня.

## P0 Единое правило целых значений

В **2.docx 13:46** прогноз назван целым с округлением к ближайшему. Для DS это задача экспортного адаптера Георгия; пользовательский CSV имеет другой формат. Не меняй молча float-поля draft API только на основании устной фразы.

С Георгием, Артёмом и Даниэлем выбери одно правило публичной выдачи. Предлагаемый вариант: сохранять точность внутри расчёта, применять сценарные коэффициенты, округлять базовое и сценарное значение каждой часовой ячейки, затем суммировать их отдельно в день/неделю/месяц. Тогда сумма видимых часов совпадает с видимым днём. Это предложение команды, а не установленный организаторами порядок.

Зафиксируй обработку ровно x,5 и числа до/после сценария. Для неотрицательных значений предлагается половина вверх. Если принимается иной порядок — показать его на примере 1,4 + 1,4 и объяснить разницу. В ответах/CSV/UI должен действовать один утверждённый вариант; старый v1 остаётся совместимым.

**Готово:** есть решение, примеры для дробей/сумм/сценариев, обновлённая схема при необходимости и подтверждение потребителей. Пока решения нет, действующий контракт не подменяется.

## P1 Долгий расчёт отдельно от выдачи

Годовой прогноз допускается считать асинхронно: **3.docx 06:08**. Существующая идея пакетного расчёта и чтения готового run подходит. Год не должен удерживать запрос обычного дневного прогноза или лишать интерфейс ранее готового результата.

Если реализуется запуск расчёта из UI, согласуй состояния «ожидает / рассчитывается / готов / ошибка», способ повторного получения результата и поведения после перезапуска. Это новые возможности только при необходимости; Redis/Celery и отдельный ML-сервис автоматически не требуются. Частично записанный результат не становится активным.

**Готово:** воспроизводимая проверка долгого задания и одновременной доступности дня, явный результат ошибки. Точные границы режима 365 дней/12 месяцев фиксирует Даниэль вместе с вами.

## P1 Минимальная защита доступа

Базовая и межсервисная авторизация названы желательными: **1.docx 07:58–08:23**. Предложение для текущей архитектуры — защита UI и API на существующем reverse proxy через HTTPS, с учётными данными из окружения/секретов. Способ утверждает Даниэль; полноценные аккаунты и роли не входят в это дополнение.

Проверь, что прямой доступ к backend не обходит защиту прогнозов и CSV, а внутренние healthcheck продолжают работать. Сейчас ML вызывается внутри процесса, поэтому отдельной межсервисной авторизации к нему нет. Она возникает только при реальном выделении сервиса.

**Готово при выборе этого пункта:** без доступа защищённые данные недоступны; учётная запись жюри работает; инструкция содержит настройку и проверку без самих секретов.
