## P0 Цель и технологические валидации

Эксперт просит исключать технологические валидации в нерабочее время из обучения: **2.docx 02:39–03:08**. Получи от Игоря версионированную маску по маршрутам и датам. Диапазон 05:30–01:00 из вопроса участника не принимай за доказанное расписание всех маршрутов.

Сравни исходный и очищенный варианты обучения на одном неизменном наборе оценочных строк. Если доступны только готовые часовые labels, не вычитай условную половину часа при старте в 05:30: запиши ограничение или пересобери цель из событий при наличии данных. Чистка train не даёт оснований молча чистить официальную оценочную цель.

Цель остаётся числом успешных валидаций, определённых в README как посадки: **2.docx 10:55–11:56**. Учитываются разные способы оплаты; пересадка не исключает успешную валидацию (**2.docx 14:32; 3.docx 00:07**). Не считать уникальные хеши вместо валидаций: мобильный NFC может менять хеш (**3.docx 01:31–02:06**).

**Готово:** есть версия маски, число исключённых событий/часов, влияние на сумму цели и качество. Игорь воспроизводит обработку; спорные часы не превращены молча в нули.

## P0 Целый конкурсный прогноз

Ответ задаёт округление до ближайшего целого: **2.docx 13:46**. Сохрани неокруглённые значения внутри модели; в submission-адаптере округляй конечные неотрицательные прогнозы. Считай финальный локальный score также после этой обработки.

Для ровно x,5 правило не дано. Предложение команде — половину вверх для неотрицательных чисел: 2,49 → 2; 2,50 → 3; 2,51 → 3. Закрепи выбранный вариант с Игорем и Даниэлем явно, не полагайся на разные значения round в библиотеках. Округление диспетчерского API согласуется отдельно с Толей.

**Готово:** один воспроизводимый экспорт, целые значения, отсутствие NaN/Inf и отрицательных чисел; метрика соответствует действительно выгружаемым значениям.

## P1 Провалы истории и представление горизонтов

С Игорем разбери хотя бы один показательный провал: ремонт/ограничение движения, потеря валидаций или неизвестная причина. Эксперт выделил поиск причины и восстановление по аналогичным периодам как полезное улучшение: **1.docx 12:11–14:19**. Не заполняй все низкие значения средним: реальные ограничения движения должны сохраняться.

Предлагаемый способ проверки восстановления — скрыть известные наблюдения в учебной части и сравнить восстановление с ними, не менять официальный эталон. Сохраняй исходное значение, причину и признак восстановления. При отсутствии подтверждённого случая достаточно отчёта об ограничении, выдумывать ремонт нельзя.

Почасовой результат должен поддерживать просмотр суток по часам, недели и месяца по дням: **1.docx 11:20–12:01; 2.docx 01:00**. Недельный просмотр — агрегация совместимых прогнозов, отдельная модель не обязательна. Согласуй с Толей порядок округления и суммирования. Долгий годовой расчёт допускается отдельно и асинхронно (**3.docx 06:08**); основной конкурсный горизонт 61 день сохраняется по прежнему README.

Ответ про утечки в коротком конкурсе (**1.docx 04:25–04:54**) подтверждает необходимость различать конкурсный ретроспективный и эксплуатационный режимы из предыдущего дополнения. Не выдавай score на поздних внешних фактах за качество будущего онлайн-прогноза. Не меняй даты доступности источников; скрытый целевой поток из ответа не становится доступным входом.

Не останавливай эксперименты только из-за 0,88: эксперт сообщил о преимуществе более высокого качества, но не дал новой формулы оценки (**1.docx 00:58–01:30**). Следующий эксперимент должен успевать пройти проверку и передачу; рабочий артефакт сохраняется.
