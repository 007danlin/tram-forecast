## 1. Результат и порядок выполнения

После выполнения человек на другом компьютере получает согласованный ML-пакет,
запускает приложение по README, выбирает маршрут и историческую дату, видит прогноз
и скачивает CSV с теми же значениями. Команда воспроизводит нагрузочный тест,
скачивает погодный архив по документированной команде и повторяет эксперименты
без сети из сохранённого snapshot. Погодный кандидат заменяет модель только после проверки пользы.

| Этап | Ответственный | Принимает | Результат, открывающий следующий этап |
|---|---|---|---|
| P0 / RUN-01 | Георгий + Толя; сборка и запуск — Даниэль | Игорь | Проверенный пакет, ready=200, воспроизводимый Compose-запуск |
| P0 / UI-01 | Артём | Даниэль + Игорь | Реальный прогноз → экран → согласованный CSV |
| P1 / LOAD-01 | Толя; окружение — Даниэль | Игорь | k6, воспроизводимые замеры, устранённые выявленные ошибки |
| P2 / WEATHER-01 | Георгий; источник и независимая сверка — Игорь | Даниэль | Загрузка → snapshot → нормализация → проверка покрытия |
| P3 / ML-02 | Георгий | Игорь + Даниэль | Раздельные погодные эксперименты, решение, повторяемый артефакт |
| FIN-01 | Даниэль + владельцы частей | Игорь | Повтор всей цепочки из чистого checkout и переданных локальных файлов |

## 3. RUN-01 — пакет, который реально принимает backend

### Вход и ответственность

Георгий передаёт Даниэлю и Толе локальный архив с моделью и прогнозом, SHA-256
архива, название модели, commit исходников, период обучения, режим информации,
список факторов, оценку качества и ограничения. Даниэль фиксирует фактический
путь в закрытой передаче. Веса и данные не загружаются в Git.

Указание каталога в старом README не доказывает наличие файлов на новой машине.
До подключения UI проверить существование пакета, checksum и импорт. При отсутствии
пакета RUN-01 не принят; синтетический fixture пригоден только для разработки тестов.

Текущий `backend.handoff.install.MEMBERS` принимает ровно следующие пути внутри ZIP:

```text
artifacts/calendar-hgbt-v1/model.joblib
artifacts/calendar-hgbt-v1/metadata.json
artifacts/calendar-hgbt-v1/feature-schema.json
artifacts/calendar-hgbt-v1/manifest.json
artifacts/forecast-for-backend.csv
```

Это транспортные имена старого handoff-контракта, не доказательство того, какая
модель находится внутри. Новый каталог `artifacts/calendar-holiday-hgbt/` сам по
себе импортёр не принимает. Для этого этапа реализовать совместимый упаковщик:
копировать выбранные четыре файла в указанные ZIP-пути без изменения байтов;
фактическое имя/режим модели сохранять в metadata. Новую схему архива вводить
только отдельным согласованным изменением с сохранением старого импорта.

**Новая команда к реализации:**

```sh
python -m scripts.package_ml_handoff \
  --artifact-dir artifacts/calendar-holiday-hgbt \
  --forecast artifacts/forecast-for-backend.csv \
  --output artifacts/releases/calendar-holiday-hgbt-handoff.zip
```

Упаковщик проверяет manifest и CSV до публикации ZIP, не перезаписывает существующий
результат, пишет SHA-256 рядом, отказывает при симлинках/неожиданных обязательных
файлах. Backend уже требует точное множество model-файлов в manifest: погодный
артефакт с дополнительными файлами нельзя молча пропустить или ослабить checksum-проверку.
Для будущей погодной модели ML-02 отдельно решает совместимость и перенос snapshot.

`forecast.csv`: разделитель `;`, точные поля из `backend/handoff/store.py:COLUMNS`,
14 640 уникальных route/date/hour строк на 10 маршрутов, 01.11–31.12.2025.
Значения не округлены; № 5 имеет `cold_start_zero_baseline`. Получение уже существует:

```sh
python -m ml forecast --artifact-dir artifacts/calendar-holiday-hgbt \
  --start 2025-11-01 --end 2025-12-31 \
  --output artifacts/forecast-for-backend.csv
```

Не смешивать forecast, metadata и model из разных запусков. Проверить, что выбранный
артефакт действительно соответствует переданному отчёту. Исходный handoff предыдущей
модели можно использовать для первого подключения, явно закрепив его версию;
новая модель заменяет его только новым полным release.

### Импорт и запуск: существующие команды

Из корня, Python 3.12; установить зависимости из `backend/requirements.txt` и
`ml/requirements.txt` для генерации модели. Сам HTTP backend использует готовый CSV.
Подставить реальный путь полученного ZIP и **новый** каталог назначения:

```sh
python -m backend.handoff.install /absolute/path/received-handoff.zip \
  --output artifacts/releases/ui-first-run
export TRAMFLOW_HANDOFF_HOST_DIR="$PWD/artifacts/releases/ui-first-run"
docker compose -f compose.yaml -f compose.handoff.yaml config --quiet
docker compose -f compose.yaml -f compose.handoff.yaml up --build -d --wait
curl --fail http://127.0.0.1:5173/api/v2/handoff/ready
python -m backend.handoff.check \
  --base-url http://127.0.0.1:5173 --release "$TRAMFLOW_HANDOFF_HOST_DIR"
```

Файл `.env`/shell-переменные пользователя не заменять. Рабочий backend уже может
занимать порт 8000: не запускать второй экземпляр на тех же портах.

Даниэль до серверной передачи дорабатывает `deploy/update.sh`: при выбранном
handoff использовать оба server Compose-файла, сохранять mount/env при пересоздании,
проверять `/handoff/ready` и ожидаемый run после обновления, сохранять предыдущую
статику и путь release для отката. Проверить два последовательных обновления
в тестовом окружении: второе не теряет пакет. Одна лишь успешная v1 health-проверка
не считается готовностью. Команды сервера — в handoff README; VPS запускается
только при отдельном разрешении на деплой.

**Приёмка RUN-01:** импорт на чистой машине; ready=200; совпадение CSV/API/дневных
сумм для всех 10 маршрутов первого дня; второй контроль 31.12.2025; после restart
тот же run; повреждённый пакет отклонён; отсутствие пакета даёт handoff 503,
без подмены синтетикой. Записать checksum и точную команду запуска.

## 4. UI-01 — реальный прогноз на существующем экране

### Сценарий и HTTP

1. При открытии: `GET /api/v2/handoff/ready`, затем `/capabilities`.
2. Получить из capabilities маршруты, допустимые даты, resolutions и ограничения.
   Выбрать первый доступный маршрут с method=model и первый доступный день;
   не использовать текущую дату сентября 2026 для пакета 2025 года.
3. Отправить `POST /query` с закреплённым `forecast_run_id` из capabilities.
4. Показать график, таблицу, total, покрытие, run и ограничения из ответа.
5. Экспортировать именно последний успешно показанный результат.

Все URL относительные с префиксом `/api/v2/handoff`. Типы и runtime-валидация —
по `backend/handoff/api.py` и работающему `/openapi.json`, не по общему v2 draft.
Пример действующего query (run добавляется из capabilities):

```json
{
  "route_ids": ["1", "5"],
  "start": "2025-11-01T00:00:00+03:00",
  "end": "2025-11-02T00:00:00+03:00",
  "resolution": "hour"
}
```

| Режим UI | Запрос | Ожидаемые строки на маршрут при полном покрытии |
|---|---|---|
| День | `[D 00:00, D+1 00:00)`, hour | 24 |
| Неделя | 7 суток, day | 7 |
| Месяц | календарный месяц, day | 30 в ноябре, 31 в декабре |

Максимум 31 сутки и 10 000 строк за query. API не поддерживает один запрос
на все 61 сутки. Границы — МСК, end исключающий; ML CLI end включающий.
Не строить МСК-полуночь через локальную зону браузера. Неделя, выходящая за
доступный период, не должна незаметно превращаться в полную: ограничить выбор
с объяснением или показать неполное покрытие по реальному ответу.

Остановки, направления, сценарные коэффициенты и численный год в этом API
не поддержаны: контролы скрыть/отключить с пояснением. Не добавлять вымышленные
фильтры. Ограничение карты из `artem-ui-layout.md` сохраняется; номера маршрутов
из API не связывать с линиями схемы без проверенного справочника.

### Отображение и состояния

- Заголовок: «Прогноз успешных посадок». Пометка: «Исторический прогноз, ноябрь–декабрь 2025».
- Удалить обязательную проверку `is_mock: true` из пути реального ответа. Если демо
  сохраняется отдельным режимом, обозначить его явно; автоматического fallback нет.
- № 5 доступен с пометкой «Нулевой baseline: нет успешной истории обучения».
- `null` — пропуск/разрыв графика, не ноль; `partial` и `no_data` видимы.
  Сумма при `available_only` называется суммой доступных значений.
- Не складывать почасовые границы интервалов для недель/месяцев; дневные bounds=null.
  Не обещать 90% надёжность: в новом отчёте фактическое покрытие ниже номинального.
- По умолчанию выводить до двух знаков после запятой; исходные float хранить целиком,
  дать увидеть исходное значение. Суммы брать из API, не из округлённых ячеек.
- При смене фильтров отменять старый запрос или игнорировать устаревший ответ.
  Экспорт заблокирован при загрузке/ошибке и пока фильтры не соответствуют показанному результату.
- Loading, empty/no_data, partial, error и retry — отдельные проверяемые состояния.
  При 503 показывать отсутствие готового пакета, при 410 — предложить обновить run,
  при 409 — повторно получить результат; автоматически другой CSV не скачивать.
- Карта не перемонтируется при query. Проверить клавиатуру, 1366×768 и узкий экран.

Recharts допустим для графика, версия фиксируется lock-файлом. Библиотека не
является условием приёмки: главное — реальные данные, доступная таблица и корректные состояния.

### Экспорт

`POST /export`: взять `response.filters`, добавить
`expected_result_id=response.result_id`. Не собирать body заново из текущих контролов.
Проверить Content-Type и `X-Result-Id`; скачать Blob и освободить object URL.
CSV backend содержит UTF-8 BOM и запятые, исходные дробные значения и версии.
Это **диспетчерский CSV**, не конкурсный `route;date;hour;prediction`.

**Приёмка UI-01:** браузерный тест проверяет день, неделю, декабрь, № 5, быстрые
смены фильтров и экспорт. Сравнение исходного batch → API → значения UI → CSV
проводится по ключам и числам с допуском `1e-9 + 1e-12*abs(expected)` до визуального
форматирования. Проверить ошибки на синтетических fixtures; smoke с реальным
пакетом — отдельно. Скриншот графика сам по себе не подтверждает числа.

## 5. LOAD-01 — измеренная производительность

Реализовать `tests/load/handoff.js`, `tests/load/README.md`, `compose.load.yaml`.
Использовать [k6 constant-arrival-rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/).
Зафиксировать версию k6/образа в инструкции, не оставлять `latest` в принятом протоколе.

Окружение: один backend-контейнер, 2 vCPU, 4 GiB, один worker исходно.
В load overlay задать `cpus: "2.0"`, `mem_limit: 4g`; по возможности исключить swap
и проверить фактические ограничения через Docker inspect. Нагрузчик — отдельно
от лимита backend; ресурсы общей Docker VM/хоста и влияние нагрузчика записать.
Запросы идут через тот же прокси, что UI. Для первой локальной проверки — Vite;
для серверных цифр отдельно проверить Caddy и явно назвать измеренный путь.

### Сценарий

- setup проверяет ready, получает capabilities/run, делает контрольный query.
  При 503/пустом каталоге/недостаточном периоде тест завершается ошибкой до нагрузки.
- Отдельный прогрев 60 секунд. Затем ступени 50, 100, 200 RPS по 5 минут;
  переходить выше только после успешной предыдущей ступени. 300 RPS — дополнительный замер.
- 70% — день/hour, 20% — месяц/day, 10% — capabilities. Использовать существующие
  методы, а не отсутствующий `/network`. Детерминированно чередовать маршруты,
  дни и комбинации маршрутов; включить № 5. В каждой итерации ровно один HTTP-запрос,
  чтобы заданная частота итераций соответствовала RPS; setup учитывать отдельно.
- POST с JSON и закреплённым run. Проверять HTTP-код, schema_version/run,
  число строк и конечные неотрицательные значения. Для небольшого набора запросов
  сверять заранее вычисленные контрольные суммы/итоги. HTTP 200 с неверным телом — отказ.
- Отдельно измерить холодный старт до ready, первый query, повторяющиеся и разные
  фильтры; называть их cache hit/miss только если кэш действительно реализован.
- Отдельно проверить большой export: 10 маршрутов × 31 день × 24 часа = 7 440 строк,
  предварительно получив query/result_id. Время export не смешивать с обычным query.

Пороги для принятия целевой ступени 200 RPS: p95 < 300 мс как общий, так и по
каждому классу query; ошибки <1%; semantic checks=100%; `dropped_iterations=0`.
Запрошенный и фактический RPS записать отдельно. Отдельно показать p50/p99,
CPU, RSS/пик памяти, число workers, размер пакета/ответа, OOM/restarts.
CPU Docker может быть >100%: указать сырой процент и долю от лимита двух CPU.
При насыщении остановить повышение нагрузки, найти узкое место, исправить и
повторить соответствующую ступень. Отчёт ниже порога — честный результат,
но требование производительности не закрывает.

**Новая команда после реализации файлов:** из shell на том же хосте, где поднят локальный Compose:

```sh
export TRAMFLOW_HANDOFF_HOST_DIR="$PWD/artifacts/releases/ui-first-run"
docker compose -f compose.yaml -f compose.handoff.yaml -f compose.load.yaml up --build -d --wait
mkdir -p artifacts/load/run-01
k6 run -e BASE_URL=http://127.0.0.1:5173 -e RATE=50 -e DURATION=5m \
  --summary-export artifacts/load/run-01/summary-50.json tests/load/handoff.js
```

В README описать отдельную команду прогрева, следующие ступени, сбор docker stats
и остановку окружения. `127.0.0.1` здесь относится к хостовому k6; контейнерный
вариант должен использовать явно настроенную сеть, не копировать этот адрес внутрь контейнера.
Не нагружать публичный VPS без отдельного разрешения. Авторизация, если включена,
берётся из закрытого окружения; секреты не входят в скрипт/отчёт.

Сырые результаты — `artifacts/load/`, сводка — `docs/verification-load.md` с датой,
commit, checksum пакета, командами, достигнутыми порогами и ограничениями.
Короткий smoke можно добавить в CI на синтетическом пакете; цифры производительности
публиковать только для указанного реального пакета и окружения.

## 6. WEATHER-01 — откуда брать погоду и как получить одинаковые признаки

### Источник и фиксированный запрос

Основной источник — [Open-Meteo Historical Weather](https://open-meteo.com/en/docs/historical-weather-api),
endpoint `https://archive-api.open-meteo.com/v1/archive`, модель `era5`.
Это реанализ; использовать его в `competition_retro`, не выдавать за выпуск прогноза,
доступный 31 октября. Разрешение на ретроспективные внешние факторы зафиксировано
в [дополнении по датасету](georgy-dataset-addendum.md#4-два-режима-внешней-информации).

Одна точка Москвы `55.7558, 37.6173`, период 01.01–31.12.2025 включительно,
`timezone=Europe/Moscow`, ISO-время. Это общегородская аппроксимация для всех
10 маршрутов, не погода на каждой остановке. Не запрашивать одинаковый архив 10 раз.

Зафиксировать параметры `temperature_unit=celsius`, `wind_speed_unit=kmh`,
`precipitation_unit=mm`, `timeformat=iso8601`, `models=era5`. Не применять best_match
и не подменять модель при сбое. Поля:

| Поле | Единица нормализованного файла | Использование |
|---|---|---|
| temperature_2m, apparent_temperature | °C | Температурная группа |
| precipitation | mm | Осадки; не складывать повторно со снегопадом |
| snowfall | cm | Отдельный признак снегопада |
| wind_speed_10m, wind_gusts_10m | km/h | Ветер |
| snow_depth | m, optional | Сейчас не используется моделью; null не заменять нулём |

Документация предупреждает о различиях доступности полей между моделями.
В старом snapshot snow_depth отсутствует полностью. Игорь проверяет фактические
`hourly_units`, coverage и происхождение ответа. Если обязательное поле, в том числе
порывы, отсутствует или всё null — получение не считается успешным. Не придумывать
значения: сохранить отчёт и исходный ответ; получить прежний проверенный snapshot
у Георгия либо оформить новый набор признаков отдельным экспериментом ML-02.

Запрос для ручного воспроизведения источника (реальные данные сохраняются вне Git):

mkdir -p artifacts/external/open-meteo/manual-2025

### Загрузчик к реализации

Добавить команду в существующий `ml/cli.py`, сетевую часть отделить от нормализации:

```sh
python -m ml fetch-weather --start 2025-01-01 --end 2025-12-31 \
  --output-dir artifacts/external/open-meteo/moscow-2025-v1
```

Команда должна создать новый каталог с `raw.json`, `request.json`, `normalized.csv`,
`manifest.json`, `coverage.json` и завершиться 0 только после всех проверок.
`request.json` содержит полный фактический URL/параметры, HTTP-статус, время начала
и успешного окончания запроса в UTC. Никаких ключей в публичных отчётах.

Таймаут соединения 10 с, чтения 120 с; максимум 2 повтора после первой попытки
для сетевых сбоев, 429 и 5xx. Уважать Retry-After; при чрезмерном ожидании завершить
с понятной ошибкой, не обходить квоту. Остальные 4xx не повторять. Проверять JSON,
API `error`, ограничить ответ 32 MiB; писать во временный каталог и публиковать
результат атомарно. Частичный ответ не становится действующим snapshot.

Повтор с существующим каталогом по умолчанию запрещён. Добавить `--offline`:
без сети проверять SHA-256 raw, повторно строить нормализованный файл во временном
месте и сверять его checksum с manifest. Для новой сетевой выгрузки нужен новый
versioned каталог. Изменённый провайдером архив не затирает результаты эксперимента.

Manifest: source_id, source_url, model, параметры/координаты запроса и ответа,
единицы, timezone, UTC offset, границы, raw/normalized SHA-256, версия нормализатора,
реальный fetched_at, information_mode=competition_retro, исключённые optional-поля,
ссылка на лицензию. `issued_at/available_at` — неизвестны, не выдумывать их.
Существующий код выводит fetched_at из mtime: для downloader исправить это на
время получения из request.json; для старого файла без receipt явно пометить
неизвестность, а mtime хранить только как файловую метку.

### Проверки данных и времени

- Ровно 8 760 уникальных часовых меток: 01.01.2025 00:00 — 31.12.2025 23:00 МСК.
- Точное равенство ожидаемой сетке, не только проверка шага между соседями.
  Отдельно 5 832 часа январь–август, 1 464 сентябрь–октябрь, 1 464 ноябрь–декабрь.
- `timezone=Europe/Moscow`, offset=10800; отсутствие дублей, пропусков, неверных
  единиц и NaN/Inf в обязательных полях. Осадки/снег/скорости неотрицательны.
- Часовые суммы провайдера относятся к предшествующему часу. Для существующей
  контрольной модели сохранить прежний timestamp-join, чтобы воспроизвести отчёт.
  Для новых экспериментов зафиксировать выравнивание: для посадок `[t,t+1h)`
  precipitation/snowfall брать из метки `t+1h`; запросить также 01.01.2026 как
  буфер, хранить его в raw, а целевую нормализованную сетку оставить 8 760 часов.
  Правило сдвига — версия preprocessing, не молчаливое изменение прежнего опыта.
- Исходный timezone оплат остаётся неподтверждённым; МСК — явная продуктовая
  интерпретация. Не скрывать эту неопределённость конвертацией.
- Join погоды к target — many-to-one по timestamp, без изменения количества
  строк и без использования будущих значений y. Пропуск — ошибка, не «сухо».

В существующей команде `prepare-weather` сохранить совместимость, усилить общую
валидацию и добавить способ использовать receipt; привести примеры в ML README
в соответствие с фактическим CLI. Backend/frontend не скачивают погоду при query.

**Приёмка WEATHER-01:** сетевой smoke на малом периоде, полный год с coverage=100%,
независимая сверка Игорем нескольких часов с raw, успешный offline-повтор; тесты
429/500/timeout, неполного ответа, пропуска часа, другой зоны/единиц, NaN/Inf и
повреждённого checksum. CI использует синтетические ответы без реальной сети.

## 7. ML-02 — отдельные погодные гипотезы и финальный пакет

Текущий `WEATHER_MODEL_COLUMNS` фиксирует все погодные признаки сразу. Добавить
явный набор групп в конфигурацию эксперимента; выбранные имена/порядок колонок,
правила выравнивания и preprocessing сохранять в feature-schema и metadata.
Провести конфигурацию через `build_hgbt_model`, evaluation, `create_artifact` и
`load_artifact`/`predict_artifact`: сейчас одного нового имени опыта недостаточно,
фабрика знает только фиксированные варианты. Отчёт selection должен содержать
выбранный config и q90 по остаткам selection; train обязан загрузить именно их,
а не молча восстановить прежний набор всех погодных колонок.
Один и тот же код строит признаки при fit и predict; не требовать отключённые
поля и не маскировать их нулями. Старый вариант оставить воспроизводимым.

Первый ограниченный набор опытов:

| ID | База + добавка | Конкретные признаки |
|---|---|---|
| W00 | Текущий официальный календарь | Контроль без погоды |
| W01 | Температура | temperature_2m, apparent_temperature |
| W02 | Осадки | precipitation, is_wet, precipitation_6h |
| W03 | Снег/переход через ноль | snowfall, is_snowing, near_freezing, freeze_transition |
| W04 | Ветер | wind_speed_10m, wind_gusts_10m |
| W05 | Все прежние группы | Воспроизведение competition_weather_hgbt |
| W06 | Лучшая обоснованная комбинация | Не более одной комбинации по результатам W01–W04 |

Для W00/W05 сначала воспроизвести прежнее выравнивание. Исправленную семантику
часовых осадков проверять отдельно на одинаковом snapshot с буфером и отмечать
суффиксом эксперимента; не смешивать её эффект с заменой модели/параметров.
Световой день — следующий кандидат после этих опытов, не зависимость их завершения.

Реализовать отдельный режим выбора без автоматического открытия сентября–октября:

```sh
# Новые флаги к реализации; сейчас backtest автоматически выполняет и holdout.
python -m ml backtest --dataset-dir "$DATASET_DIR" \
  --weather-factors artifacts/external/open-meteo/moscow-2025-v1/normalized.csv \
  --stage selection --experiment-config ml/experiments/weather-groups.json \
  --output artifacts/experiments/weather-groups/evaluation.json \
  --experiment-log artifacts/experiments/weather-groups/experiment-log.csv
```

Конфиг без данных можно хранить в Git. Публичный журнал обновлять после проверки,
не перезаписывать прежнюю историю экспериментов пробным запуском.

Использовать прежние expanding folds: train январь–апрель → май–июнь;
train январь–июнь → июль–август. Второе окно имеет 62 дня: сохранить его для
сопоставимости, указать точную длину и отдельный срез дней 1–61. Основной submission
всегда 61 день. Никакого случайного train/test split или target из горизонта.

Сентябрь–октябрь уже открыт прежними работами. Не называть новый результат
на нём «первым независимым holdout». После фиксации нового выбора допускается
контрольная оценка с явной пометкой повторного использования и без последующего
подбора. Отчёт сравнивает одинаковые ключи, target-маску, seed и snapshot;
изменение очистки цели — отдельный опыт, а не часть погодного прироста.

Критерий включения погодного варианта: общий WAPE-score выше W00 и положительный
эффект на обоих selection folds; не ухудшает MAE каждого поддержанного маршрута
более чем на 5% относительно W00. Это внутренний guardrail ТЗ, не правило конкурса.
Показать также пики/выходные/дни 1–7, 8–30, 31–61 и неопределённость сравнения.
Если критерии не выполнены, сохранить календарную модель; отрицательный результат
с воспроизводимыми данными закрывает экспериментальную задачу.
