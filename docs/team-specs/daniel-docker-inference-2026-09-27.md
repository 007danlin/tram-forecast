## 1. Цель и результат

Дать жюри воспроизводимый способ запустить принятую конкурсную модель в Docker
и получить прогноз из её сохранённых весов. Контейнер должен рассчитать полный
прогноз и submission без доступа к заранее рассчитанным ответам. Затем отдельная
проверка сравнивает результат с принятым конкурсным CSV.

Сохранить действующий продукт: рассчитанный прогноз упаковывается в прежний
handoff, а FastAPI/React выдают и показывают его. Обучение, модельные параметры,
HTTP-контракты и поведение интерфейса этой задачей не меняются.

Готовый результат — Dockerfile, автоматизированная проверка, инструкция запуска,
локальные доказательства воспроизведения и комплект исходников, из которого
проверка повторяется без окружения разработчика.

## 4. Реализация

### 4.1. Отдельный вычислительный образ

Создать `ml/inference/Dockerfile` с CLI-входом `python -m ml`. Использовать
Python 3.12 и существующие точные inference pins; зафиксировать фактическую
версию Python, базовый образ/digest, платформу и итоговый image ID в протоколе.
Начать с версии, соответствующей проверенному окружению B2. Если для Linux
недоступен pin/образ, разобраться и документировать изменение, не обновлять
ML-библиотеки до произвольного latest ради успешной сборки.

Копировать только нужные исходники и зависимости. Веса, реальные данные,
эталонный CSV и прогнозы в образ и Git не включать; исключения `.dockerignore`
сохранить. Образ не должен запускать fit, обучение, подбор или скачивание погоды.

После сборки запускать с `--network none`. Модель и sample монтировать только
для чтения, результаты — в новый локальный каталог. Не монтировать целиком
репозиторий, Downloads, G0-пакет или каталог с готовыми прогнозами. Отсутствие
этих входов должно быть видно в фактических mounts команды/inspect.

Обычный веб-запуск сохраняется. Compose для one-shot inference необязателен;
если добавлен, использовать отдельный файл/явный profile без автоматического
запуска при штатном `docker compose up` и без новых публичных портов.

### 4.2. Использовать существующий расчёт

Внутри нового образа должны работать существующие команды:

```sh
python -m ml forecast \
  --artifact-dir /model \
  --start 2025-11-01 --end 2025-12-31 \
  --output /output/forecast.csv

python -m ml submission \
  --artifact-dir /model \
  --template /input/test_submission.csv \
  --scope sample \
  --output /output/submission.csv \
  --preflight-output /output/submission.preflight.json
```

Это уже существующий CLI; `/model`, `/input`, `/output` — предлагаемые точки
монтирования нового образа, а не готовый контейнер. В итоговом README привести
полные проверенные `docker build` и `docker run`, подготовку каталогов и mounts.

`forecast` сохраняет float, reference, интервалы и статусы. `submission`
применяет прежнее `floor(x + 0.5)` один раз после ансамбля, сохраняет порядок
sample, `;`, UTF-8 и полный состав строк. Обе границы дат CLI включены;
полуоткрытую семантику HTTP в этот CLI не переносить.

Проверка manifest выполняется до загрузки model; при ошибке нет подмены CSV,
синтетикой или новой моделью. Не использовать новый fit, округление весов,
ручную правку строк, поправку к прогнозу или повторную калибровку.

### 4.3. Проверка и доказательства

Добавить проверочный скрипт, например `scripts/verify_container_inference.py`,
и инструкцию его запуска без обязательной host-venv. Он должен возвращать
ненулевой exit code при несоответствии и сохранять машиночитаемый отчёт.
Сравнение с эталоном выполняется отдельным шагом **после inference**; эталон
не передаётся вычислительному процессу. Контрольные SHA разрешены.

Провести следующий ограниченный набор:

| Проверка | Условие успеха |
|---|---|
| Два полных независимых запуска | Новые контейнеры и выходные каталоги, без сети и fit; результаты совпали между собой |
| Submission против B2 | Все 14 640 ключей, порядок и целые значения точны; SHA ожидаемого CSV совпал; прежний preflight passed |
| Float против B2 | Сверены ключи, статусы, prediction, reference, lower/upper и priority; отдельно записаны SHA/побайтное и численное совпадение |
| Несколько диапазонов | Отдельно рассчитать 01.11, 15.11 и 31.12; сравнить со срезами полного расчёта; в каждом есть 10 × 24 строки |
| Шаблон не источник ответов | На временной копии sample заменить только `prediction` на контрольные числа; пересчёт даёт прежний submission. Оригинал не менять |
| Ошибочные входы | Отсутствующая модель, повреждённый model/checksum и некорректный sample дают ошибку без fallback и успешного отчёта |
| Защита результата | Существующий output не перезаписывается; входы до/после имеют прежние hashes |

Для первого прогона целевое условие — точное воспроизведение всех файлов B2.
Если платформенные различия дали иной float, сохранить diff: число отличий,
максимальную абсолютную/относительную ошибку, влияние на округлённый DS и
конкретные версии/архитектуру. Не менять веса и не подбирать допуск после
результата ради статуса pass. Отдельное решение о численной эквивалентности
должно быть явно документировано; изменение целых DS-значений не считается
воспроизведением принятого champion. Не выдумывать официальный допуск жюри.

Проверка нескольких дат подтверждает параметризованный расчёт. Не называть
её тестом организаторского потока, онлайн-обучением или обработкой NDTP.

В `artifacts/inference-docker/<new-run>/` сохранить команды, exit codes,
stdout/stderr, hashes входов/выходов, preflight, отчёт сравнения, версии,
image ID/digest, архитектуру CPU, лимиты и настройки потоков. Реальные прогнозы
и исходные доказательства остаются вне Git; в документацию включить сводку.

### 4.4. Связь с существующим сервисом

Полученный float CSV упаковать через существующий
`python -m scripts.package_ml_handoff`, затем импортировать штатным
`backend.handoff.install` в **новый локальный release**. Не подставлять
четырёхколоночный округлённый submission вместо float handoff.

В изолированном локальном веб-запуске проверить ready, срезы первой/последней
дат, № 5, дневные суммы и закреплённый CSV против нового расчёта. Использовать
существующие handoff-проверки; простой просмотр UI должен подтвердить, что он
показывает этот release. Не перезапускать и не заменять публичный сервис.

Схема после реализации должна быть честно описана:

```text
Проверенный ML-артефакт → Docker CLI inference → новый float CSV
  → существующая упаковка/проверка handoff → FastAPI → React / CSV
```

Это последовательность подготовки прогноза и его выдачи, а не исполнение
модели на каждом HTTP-запросе. При точном совпадении файлов существующий run
может сохраниться; при отличиях показать причину нового run.

### 4.5. Измерения и комплект сдачи

Измерить отдельно время запуска контейнера с расчётом, длительность полного
inference при доступном измерении, число строк и наблюдаемую память. Начальный
контрольный профиль — 2 vCPU / 4 GiB без дополнительного swap; записать реальные
лимиты, thread settings и архитектуру. Не выдавать единственный прогон за p95,
а отсутствие OOM — за измеренный пик RAM.

Старые 200 RPS / p95 относятся к выдаче готового handoff. Не приписывать их
модели и не запускать новый длительный нагрузочный тест API без причины.
Сборка образа может требовать сети; запуск готового образа и inference — нет.

Обновить README проекта, ML README, архитектуру, `INTEGRATION.md`, инструкцию
сдачи и поля A1/A3/A4/A5 в пределах фактически реализованного результата.
Добавить `docs/submission-final/docker-inference-verification.md` с условиями,
проверками, ограничениями и ссылками на локальные доказательства.

Проверить состав локального архива исходников. У
`scripts.package_submission_prep` явные списки путей/расширений; новые файлы
добавить в правила упаковки при необходимости, а untracked-исходники — в
проверенный `--include-list`. Не делать commit ради попадания файла в архив.
Собрать и запустить inference из распакованного комплекта в чистом каталоге:
без developer-venv, host Python для ML и ссылок на личный Downloads. Отдельные
модель/sample передаются явно, данные не становятся частью source ZIP.

## 6. Объём работ и итог исполнителя

Не входят: новые ML-эксперименты/обучение, исправление score через подгонку,
изменение champion, новые HTTP-контракты, редизайн, телеметрия/NDTP,
брокер сообщений, деплой, отправка на платформу, commit/push или публикация.
Материалы и ограничения уже принятых исходных training provenance не переписывать.

В итоговом ответе исполнителя нужны: что реализовано; точные команды;
принятая модель/CSV SHA; результаты проверок и замеров; пути к инструкции,
локальному комплекту и протоколу; конкретные незакрытые вопросы, если они есть.

воспроизведением B2. Если потребуется изменение чужого контракта, сначала
