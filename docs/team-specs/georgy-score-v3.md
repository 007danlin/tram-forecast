## 2. Правила проверки, которые нельзя обойти подбором

Метрика — `max(0, 1 − sum(abs(y − floor(p+0.5))) / sum(y))` по всем строкам
соответствующего набора. Прогноз должен быть конечным и неотрицательным;
для среза с `sum(y)=0` score не определён, показывать SAE/MAE и null.
Основной результат —
глобальная сумма ошибок, не среднее route-score и не среднее score folds.
Показывать raw и rounded, выбирать по rounded. Округление одно, в самом конце.

Для каждого опыта сохранить SAE, sum(y), bias, runtime, seed, config,
fingerprints, OOF и срезы: маршрут, час, будни/выходные/официальный тип дня,
горизонт 1–7 / 8–30 / 31–61, каждый fold. Сравнивать при одинаковых ключах.
№ 5 с нулевым y не меняет WAPE, но меняет MAE, если входит в число строк.

S1–S4 перекрываются и содержат лишь 153 уникальные даты. D многократно
использовалось и пересекается с S4: это **не независимый финальный holdout**.
Не выбирать смесь, источник или порог по D, не называть его новым доказательством
обобщения. До очередного просмотра D заморозить config выбранного кандидата.
Если D не проходит порог, не перебирать на нём запасные смеси до успеха.

Для калибровки, early stopping и обучения метамодели нужны внутренние
хронологические origins. У каждой обучающей метастроки target должен быть
известен до origin оцениваемого прогноза. Нельзя обучить веса на всём S1
и оценить S2: S1 заканчивается 30.06, а origin S2 — 31.05.
На ранних origins с малой историей использовать фиксированную простую смесь.

На shortlist дополнительно проверить парную разницу ошибок блочным bootstrap
по 7-дневным блокам целевых дат, сохраняя вместе маршруты, часы и повторения
даты из разных origins. Это диагностика устойчивости зависимых данных,
не новое независимое испытание. Отдельно показать score по уникальным датам
при заранее фиксированном правиле выбора origin; не заменить этим основной протокол.

Два независимых режима: `operational` и `competition_retro`.
Во втором допускаются фактическая погода/внешние события согласно уже записанному
конкурсному уточнению; будущий пассажиропоток запрещён в обоих. Сравнивать
эффект источника с baseline того же режима. Для operational использовать только
известное на origin; выданные позже прогнозы погоды не подходят.

## 3. Очерёдность экспериментов

### P0 — полный fit и календарный перенос

**F1.** Отключить `early_stopping` у B0/B1, сохранив их признаки, loss,
число итераций и остальные параметры. Сейчас auto-validation резервирует
часть train, при этом оба компонента во всех проверках доходят до лимита итераций.
Это гипотеза о полезности полного train, не найденная утечка target.

**F2.** Отдельно сравнить временную inner-validation с последующим fit всех
разрешённых train-строк на найденном числе итераций. На direct-данных отделять
по доступности target, а не случайным строкам одного дня.

**K1.** Добавить переносимый `effective_day_type`: официальный рабочий день,
обычный выходной, праздник; выходной и рабочая суббота должны использовать
обучавшиеся режимы. Raw day-of-week сохранить отдельным признаком/абляцией.
Проверить 01.11, 03–04.11, 31.12. Константный в train `is_working_weekend`
не может сам научить модель рабочей субботе; значение потока не придумывать.

**K2.** Отдельная абляция month/ISO-week против гладких сезонных признаков,
темноты/длины дня и сезонных аналогов января–марта. Recency 90 дней ослабляет
единственную наблюдённую зиму: проверить сочетание недавнего уровня с зимней
формой суток, не копируя январскую величину целиком в декабрь. Граница сезона,
вес аналога и нормировка подбираются только на разрешённой истории.

### P1 — прямой прогноз из origin на 61 день, обязательный запуск

Использовать `score_direct` в `ml/score_models.py` как отправную точку,
проверив генератор обучающих примеров. Его прежний synthetic smoke не заменяет
реального опыта. Не ставить запуск в зависимость от провала более простой модели.

Один пример: `(route, origin, target_date, hour, horizon_day)`.
Origins с шагом 14 дней, минимум 56 дней истории, горизонт 1–61; шаг 7 дней —
следующая абляция, если начальный опыт перспективен. Использовать только
targets, доступные к внешнему cutoff; не размножать короткие горизонты
неограниченно из-за обрезанных origin-окон. Зафиксировать веса горизонтов и
повторяющихся targets до оценки.

Признаки из истории **до origin включительно**:

- Уровни/медианы за 7, 14, 28, 56 дней; отдельно route-day и
  route-hour-effective-day-type, число наблюдений и надёжность профиля.
- Отношения недавнего уровня к предыдущему, устойчивый локальный наклон,
  доля нулей и число аномальных дней. Регуляризовать по числу наблюдений;
  clipping/порог выбрать на train, не по прогнозным провалам.
- Отклонение маршрута от общего уровня остальных маршрутов в прошлом;
  прошлый режим будней/выходных и время после обнаруженной смены режима.
- Известные target-календарь, горизонт и подтверждённые внешние факторы.

`y[target_date−7]` недоступен для большинства дальних дней. Добавлять такой lag
можно только с проверкой даты относительно origin и индикатором доступности;
основой должны быть origin-агрегаты. Не подставлять будущие фактические
валидации, количество активных валидаторов, машин или рейсов внутри горизонта.
Эти raw-поля можно изучать на прошлой истории для диагностики режимов.

Начальная пара: CatBoost MAE и вариант squared/RMSE с той же информацией.
Вторую архитектуру HGBT проверять при ресурсе, без повторения большой сетки
старого CatBoost без origin-признаков. Loss сравнивается по итоговому WAPE.

### P1 — отдельная модель суточного уровня и почасовой формы

Построить `p(route,date,hour) = predicted_daily_total × hourly_share`.
Hourly share неотрицательна, сумма по 24 часам равна 1; fallback к общему
профилю задаётся заранее. Окончательные метрики считать на почасовых строках.

Базовый суточный уровень — устойчивый профиль последних недель того же
официального типа дня. Учить поправку к нему на origin-признаках, горизонте,
календаре и режиме движения. Сравнить абсолютный residual и нормированный
residual/ratio. При нормированном target подобрать веса так, чтобы не сменить
задачу на равный процент ошибки всех маршрутов; проверить итоговую SAE
в исходных единицах, не добавить второе неявное взвешивание по объёму.

Форму суток брать из истории на origin с усадкой route-day-type к общему
профилю; сравнить недавнюю и сезонную форму. Первый опыт — без погоды/событий,
следующий добавляет режим. Это отличается от уже проигравшего daily-HGBT:
обучение на многих origins, поправка к актуальному уровню и явный горизонт.

Диагностика: daily SAE, hourly SAE, bias, доля ошибок уровня; отдельно случаи
малого суточного потока. Истинные суточные суммы использовать только в
помеченной oracle-диагностике, никогда в подборе рабочего прогноза.

### P1 — режимы 7, 17 и 50

Сначала закончить карточки T01–T09 из реестра источников. Приоритет:

1. **7/50 с 10 июля:** сокращение № 7, объединение 13/50 на срок до 28 дней.
   Проверить окончание и как объединение отражено в `ngpt_route`/валидаторах.
2. **17 с 5 и 26 апреля:** разные виды ограничений по выходным; восстановление
   не выводить из отсутствия следующей новости.
3. **50 в сентябре–октябре:** почти нулевые выходные на фоне большого буднего
   потока. Ночное объявление с 12 сентября не объясняет весь день. Проверить
   raw-покрытие устройств/маршрута и независимый источник, не восстанавливать y.
4. **Ноябрь–декабрь:** ограничения 7/50, запуск Т1 и изменение пересадок.
   Объявление о Т1 не задаёт произвольный процент оттока с № 50.

Разделять подтверждённое полное закрытие, частичное сокращение, косвенное
влияние и неизвестную причину. Неполный интервал даёт признак неопределённости,
а не вечную маску. Состояние «низкий наблюдаемый поток» можно прогнозировать
по прошлому, но нельзя переименовывать в доказанное `no_service`.

Сравнить признаки режима и двухрежимную модель с усадкой; сохранять все target.
Изменение метки/очистка — отдельная подтверждённая маска Игоря и отдельный опыт.
Исторические маршруты не объединять без доказательств; закон сохранения суммы
посадок между маршрутами при перенаправлении пассажиров не предполагается.

### P2 — источники для остатков модели, затем ансамбль

После сильного календарно-исторического контроля проверить отдельно:

- **Погода:** существующий buffered Open-Meteo snapshot с нормализацией
  `next_hour_accumulation_v2`; осадки/снег/ощущаемая температура и взаимодействия
  с часом и типом дня в residual/daily-модели. Уже проигравшую W01–W05 не повторять
  как новый результат. Не сдвигать осадки на час второй раз.
- **События:** 2–3 реально связанных с маршрутами площадки, сначала ВДНХ,
  затем конкретные спортивные/массовые события при подтверждённой географии.
  Архив KudaGo — поиск кандидатов; первоисточники — организаторы и клубы.
  Нужны события и аналоги до origin, а не только ноябрь–декабрь.
- **Дополнительный календарь:** каникулы/сессии конкретных учреждений у линии,
  метрополитен/ЦППК — только подтверждённые пересадочные ограничения.

Для событий сохранить место, сеансы, начало/окончание, повторяемость, тип,
привязку к маршруту/остановке и источник. Проверить окна приезда/отъезда;
длительная выставка не создаёт круглосуточный event=1. Оценивать эффект по
прошлым аналогам с регуляризацией. Если аналогов/покрытия нет, источник остаётся
сценарным: выдуманный множитель или посещаемость не становятся ML-признаком.

Геометрический буфер — внутренняя гипотеза. Проверить несколько заранее заданных
радиусов пешей доступности (например, 400/800 м) на train и вручную проверить
связь; современная трасса не гарантирует историческую. Без геометрии допустимы
только явные маршрутные ограничения из источника, не привязка по названию района.

Ансамбль строить из OOF с разными ошибками. Сначала фиксированная малая сетка
весов B2 + лучший direct/daily; затем регуляризованная калибровка, если хватает
хронологических meta-данных. Проверить bias и сезонную устойчивость scale.
Не выбирать 1,00 вместо 0,96 только потому, что это лучше на D; не делать
отдельный коэффициент для каждой даты/маршрута по будущему y.

## 4. План запусков и критерии отбора

Первый проход: не более **24 новых конфигураций обучения** сверх B0/B1/B2;
ориентир распределения — 4 fit/calendar, 4 direct, 4 daily, 4 regime,
4 weather/event, 4 резервных для перспективной ветви. Это лимит первичного
поиска, не причина пропустить direct или daily. Кэшировать общие fits/OOF;
перебор нескольких фиксированных смесей не требует повторного обучения.
При нехватке времени сначала сократить резерв и слабые внешние источники.

На старте сохранить численные пороги в config, по умолчанию использовать
уже принятые в v2, но сравнивать **с B2 на новом общем протоколе**:

- общий прирост S1–S4 не менее **+0,002**;
- улучшение минимум на **3 из 4** folds;
- худшая разница отдельного fold и horizon-среза не ниже **−0,003**;
- MAE любого модельного маршрута не хуже B2 более чем на **5%**;
- на повторной D после заморозки — не ниже B2 более чем на **0,003**.

Рядом всегда показывать B1: кандидат, проигрывающий ему на поздних origins,
требует объяснения сезонного поведения. Для близких результатов до 0,0005
предпочитать более простую модель; повторить только финалиста на втором seed.
Порог нельзя ослабить после неудачного результата и объявить это тем же опытом.
Перспективный кандидат вне guardrails — отдельный исследовательский результат.

Если ни один кандидат не проходит, сохранить прежний release и оформить
`no_improvement` с причинами. Не называть это достижением цели 0,90. Если
улучшение есть, продолжать следующую небольшую серию по оставшемуся вкладу SAE,
а не механически расширять сетку до score 0,95 на просмотренных данных.

Первые контрольные результаты: версии/контроли и fit/calendar; затем
обязательные direct/daily; затем проверенные режимы, residual-факторы и смесь.
После каждого блока — таблица выигрыша и стоимости следующего шага. Реальный
срок оценить после первых fits, сохранить запас на финальное обучение и preflight.

## 5. Приёмка и поставка

Сдать config v3, код воспроизведения, журнал **всех** опытов, отчёт с абляциями,
OOF каждого finalist, таблицу источников/покрытия и явное решение о champion.
Сырые данные, события и snapshots, OOF с реальным target, модели и CSV остаются
в игнорируемом `artifacts/`; в Git — код, агрегированные выводы и ссылки.

Для принятого кандидата: fit на январе–октябре, новый artifact/metadata,
sample-совместимый CSV, preflight и SHA-256; связать их с config, исходниками,
train cutoff, зависимостями, режимом информации и результатом оценки.
Платформенный score до реальной отправки — null. Результат Даниэля 0,83732
сохраняется у прежнего файла, не переносится на новый.

Минимальные содержательные проверки реализации:

1. Изменение target после origin не меняет признаки/предсказание этого origin;
   проверка на часовом lag, direct-training и regime detection.
2. Для operational поздняя публикация или forecast run не попадает в признаки;
   для retro есть честная отметка времени и воспроизводимый snapshot.
3. Календарные граничные дни, 61 сутки, пересечение полуночи и частичные
   ограничения: часы не удаляются, часть маршрута не становится полным нулём.
4. Serialization round-trip сохраняет прогноз; fresh-process inference
   использует тот же feature schema и snapshot, не обращается к текущему вебу.
5. Полная точная сетка sample, отсутствие дублей/NaN/отрицательных значений,
   однократное округление, 1 464 нуля № 5; preflight сравнивает порядок/ключи.
6. ML regression checks, затем штатный package/import в новый временный каталог
   при поставке handoff; UI/API/CSV используют один и тот же новый run после
   отдельно разрешённого обновления, не смешивают новый CSV и старые metadata.

Обновить ML README, model-card и INTEGRATION вместе с реализацией: отдельно
работающий код, локальный выбранный кандидат, отправленный CSV и серверный
release. Изменять сайт ради DS-score не требуется; внешние источники получать
на этапе подготовки snapshot, не при открытии графика пользователем.
