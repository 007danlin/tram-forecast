# ТЗ для Codex: TramFlow — «Вечерняя смена» с двумя темами

Дата: 26.09.2026. Статус: **направление выбрано Даниэлем; спецификация для реализации**. Документ не означает, что редизайн уже реализован или опубликован.

## 1. Задача и обязательный результат

Переделать **действующий интерфейс TramFlow** по выбранному варианту C «Вечерняя смена». Пользователь одобрил именно его внешний вид: сохранить композицию, пропорции, спокойные тёмные панели, крупные показатели, светлую трамвайную схему и красные акценты. Добавить переключение тёмной и светлой темы. Светлая тема — белые поверхности, красный Московского транспорта, тёмный текст; та же компоновка и те же функции.

Результат — работающие компоненты существующего React-приложения, подключённые к действующему handoff API, адаптивные на телефоне и компьютере. Довести существующую интерактивную схему Артёма до визуальной близости к исходной карте. Реализация должна запускаться штатными командами проекта, собираться для существующего сайта и сохранять прогноз, таблицу, таймлайн и CSV.

**Визуальное соответствие C — обязательный критерий приёмки, а не свободная интерпретация.** Не заменять выбранную композицию вариантом A/B, типовым dashboard с множеством плиток или новой концепцией. Не просить пользователя повторно выбрать направление.

## 3. Композиция «Вечерней смены»

### 3.1. Компьютер

Главный экран строится на CSS Grid/Flex, без фиксированного позиционирования всего макета по координатам Figma.

| Область | Эталон 1280 × 800 | Правило реализации |
|---|---|---|
| Шапка | Высота 72; боковые поля 28 | TramFlow слева; «Карта и прогноз», «Аналитика», «О данных», тема справа |
| Фильтры | От y=72; высота 74; поля 16; gap 8 | Маршрут, дата МСК, День/Неделя/Месяц, исторический режим; при нехватке ширины перенос |
| Рабочая область | Начало y=146; поля 20; gap 20 | Карточка слева, карта с таймлайном справа; верхние границы совпадают |
| Карточка | x=20, y=166; ширина 356, высота около 500 | Padding 20, gap 12, radius 12; высота растёт под данные и сообщения |
| Колонка карты | x=396, y=166; ширина 864 | `minmax(0, 1fr)`; основная площадь экрана принадлежит карте |
| Карта | 864 × 474; radius 12 | Светлая схема, без перекрытия карточкой; controls внутри собственного контейнера |
| Таймлайн | Под картой; gap 16; высота 74 | Кнопка проигрывания, выбранный интервал/значение, шкала |

Размеры — ориентир при 1280 × 800 и обычном тексте, не ограничение на динамический контент. Новому переключателю темы выделить место в шапке, сохранив композицию. Видимая высота контролов 42–44 px; фактическая область нажатия минимум 44 × 44 px.

На больших экранах увеличивается преимущественно карта; карточка остаётся 356–380 px. Не растягивать текст и контролы пропорционально viewport. При 1024–1199 px карточка 320 px, gap 16. Если при увеличении текста две колонки перестают помещаться, включить одно­колоночное представление раньше, без обрезки.

Высоту карты рассчитывать от доступного пространства с нижним пределом 360 px на desktop. При небольшой высоте окна или развёрнутой таблице допускается вертикальная прокрутка страницы. Не удерживать все блоки в одном экране ценой обрезанного CSV или сообщений.

«Карта и прогноз» — основное представление. Сохранить возможность свернуть прогноз и вернуть его понятной кнопкой: в этом режиме карта расширяется на освободившееся место. Панорамирование и масштаб сохраняются. Раздел «Аналитика» показывает тот же результат в расширенном виде.

### 3.2. Телефон и планшет

При ширине менее 1024 px — одна колонка. Основной мобильный эталон: 390 × 844.

- Шапка около 64 px: бренд, переключатель темы и компактное меню навигации. Доступны «Карта и прогноз», «Аналитика», «О данных».
- Следующая строка около 66 px: маршрут, дата, «Ещё». В «Ещё» доступны День/Неделя/Месяц и сброс. Активный период виден в кратком контексте, даже когда меню закрыто.
- Светлая карта непосредственно под фильтрами; на 390 × 844 её высота около 286 px. Рабочее правило: `clamp(240px, 34dvh, 380px)`. Не скрывать карту под невидимой полноэкранной панелью.
- Под картой — компактная карточка: заголовок и дата, исторический режим/МСК, итог, пик, покрытие, «Скачать CSV», «Обновить», кнопка раскрытия графика/таблицы/сведений. Поля 18 px, верхние углы 20 px, высота по содержимому, ориентир 294 px.
- Таймлайн расположен ниже карточки и остаётся доступен прокруткой. Раскрытие прогноза добавляет контент в поток; не накрывает обязательные действия. Кнопка раскрытия имеет `aria-expanded` и работает без жеста перетаскивания.
- «Схема: увеличить» открывает увеличенную карту в доступном полноэкранном слое с явной кнопкой закрытия. Это та же камера и выделение, без повторной загрузки сети и сброса при возврате.
- При 768–1023 px сохранить последовательность блоков; выделить карте больше высоты, не растягивать компактную сводку пустыми колонками. В горизонтальном телефоне обеспечить прокрутку и доступность действий.

Использовать `100dvh` с fallback и safe-area inset там, где есть полноэкранные слои. При фокусе поля и открытой экранной клавиатуре дата/кнопка закрытия остаются достижимы. Горизонтальной прокрутки страницы нет; отдельная широкая таблица может иметь подписанный прокручиваемый контейнер.

## 4. Две темы

### 4.1. Поведение переключателя

Первое открытие без сохранённого выбора — **тёмная «Вечерняя смена»**, независимо от системной темы. Два варианта: «Тёмная» / «Светлая», без третьего автоматического режима в этой поставке.

На desktop — компактный двухпозиционный переключатель в правой части шапки. На телефоне допустима одна кнопка солнце/луна, доступное имя которой описывает действие: «Включить светлую тему» / «Включить тёмную тему». Иконки из одного SVG-набора, не emoji. Текущее состояние не передаётся только цветом. Доступны Tab, Enter/Space и видимый focus.

Хранить `dark | light` в `localStorage` под одним версионированным ключом, например `tramflow.theme.v1`. Любое другое значение трактовать как отсутствующее. Чтение/запись — с обработкой исключений; недоступный storage не мешает работе и переключению в текущей сессии.

Тема применяется через `data-theme` на `document.documentElement` до первого видимого кадра. Устранить вспышку светлого экрана при сохранённой тёмной теме; инициализация не ждёт API или загрузки React. Согласовать способ ранней инициализации с действующей CSP, не ослаблять её. Настроить `color-scheme` для нативных контролов.

Переключение не перезагружает страницу, не вызывает forecast API, не прерывает скачивание CSV, не сбрасывает маршрут, дату, горизонт, выделенный час, режим графика, раскрытую карточку, pan/zoom или проигрывание. Корневой компонент не должен получать `key={theme}`.

### 4.2. Цветовые токены

Обе темы используют одни компоненты и семантические CSS variables. Не размножать стили через произвольные `dark ? ...` и inline hex. Значения ниже — стартовая спецификация; проверять реальные сочетания при реализации.

Светлая тема должна восприниматься белой с красными сигналами Московского транспорта. Серые поверхности служат разделению блоков; не заливать весь экран красным. Активный период и основное действие — красная заливка с белым текстом; вторичные действия нейтральные. В каждой теме проверить hover, active, focus, disabled, loading, error, empty, selected.

Официальный красный `#E4000D` подтверждён в основном [брендбуке МТ](https://t.mos.ru/common/20221006/BB_part_1+2+3_MT%20Folder.zip), часть 3, §3.2.3, PDF-страница 14 / печатная 27. Тёмные и вспомогательные UI-цвета — решение TramFlow, не официальный набор МТ.

Белый текст на `#E4000D` имеет расчётный контраст около 4,88:1. Сам `#E4000D` на тёмной панели `#1D3343` — около 2,68:1, поэтому тонкую линию графика, focus и мелкий активный текст на ней заменить близким `#FF6470` (около 4,55:1). Это точечная коррекция читаемости выбранного макета, без изменения композиции и фирменных кнопок. Цвет не является единственным носителем статуса.

### 4.3. Типографика и детали

Для визуального совпадения с выбранным C основная гарнитура этой поставки — **Manrope с кириллицей**, как в эскизе. Привести кнопки, поля и цифры к той же семье: Inter внутри библиотечных кнопок Figma — техническая особенность эскиза, не требование смешивать шрифты.

Moscow Sans подтверждён брендбуком, но его автоматическая подмена изменила бы выбранный пользователем вид. Не блокировать интеграцию ожиданием шрифта и не менять Manrope на Moscow Sans в этой поставке. Брендовый характер светлой темы задают палитра, иерархия и сдержанная навигация. Это уточняет предварительное предложение о Moscow Sans в исследовании.

Шрифт поставлять локально в web-формате из проверенного источника с допустимыми условиями распространения и файлом лицензии; runtime не должен зависеть от Google Fonts/CDN. Лицензию самого проекта не менять. До загрузки работает `system-ui, sans-serif`; `font-display: swap`. Ограничить набор необходимыми начертаниями/одним variable-файлом, сохранив кириллицу.

Ориентиры: основной текст 14–16 px / 20–24; пояснения 12–13 / 17–19; заголовок карточки 20–22 / 28–31; главный итог 44 / 52 desktop и 36 / 44 mobile; интерфейсные подписи 14 / 20. Цифры табличные (`tabular-nums`). Не уменьшать длинный итог до мелкого текста; переносить или расширять блок. Подписи карты имеют собственный масштаб и не заменяются глобальным UI-шрифтом без проверки геометрии.

Скругления: панели/карта 12 px, кнопки 8 px, мобильная карточка сверху 20 px. Скруглённая внешняя рамка desktop и рамка устройства в Figma не нужны на краях viewport. Тени слабые, только где нужно отделить меню/диалог. Без стекла, тяжёлых градиентов, свечения и декоративной анимации. Переходы 120–180 ms; `prefers-reduced-motion` отключает необязательное движение.

## 5. Содержимое и рабочие сценарии

### 5.1. Фильтры

Доступные маршруты, даты и шаги — из `capabilities`; не копировать в код список и дату из эскиза. Начальная дата соответствует доступному историческому пакету, а не сегодняшнему дню.

День использует часовые точки, неделя — 7 календарных дней, месяц — полный календарный месяц по существующему контракту. Период вне покрытия блокируется с объяснением до запроса. Отображение всегда в МСК, включая календарь и таймлайн.

Показывать работающие контролы. Остановку, направление, год, сценарий и неработающее избранное убрать с главной панели; соответствующие ограничения оставить доступными в «О данных». Это сокращение визуального шума не означает выполнения недостающих функций.

### 5.2. Карточка и аналитика

Порядок карточки повторяет C:

1. Маршрут, выбранная дата/диапазон.
2. «Исторический прогноз · МСК».
3. Крупный итог и точная единица: «успешных посадок за день/период».
4. Пик и покрытие. Для суток — пиковый час, для недели/месяца — дата максимума; не называть дневную агрегацию пиковым часом.
5. Переключатель «График / Таблица» и данные; на телефоне — после раскрытия.
6. Основная кнопка «Скачать CSV», вторичная «Обновить».
7. «Данные и ограничения» с полными сведениями.

Если максимум не определён (все значения null), показывать «Нет данных». При равных максимумах обозначать несколько интервалов или явно писать «Первый максимум», не приписывать одному случайному часу уникальный пик. В численном нулевом baseline не обещать отсутствие движения.

Числа Figma не переносить в код. Крупный итог приходит из API; форматирование до двух знаков в UI допустимо по действующему правилу. Полная точность остаётся в таблице/подробностях и CSV. Дробные значения не выдавать за точное число уникальных пассажиров.

Сохранить полную таблицу, единицы, статусы/покрытие строк, синхронизацию выбора графика и таймлайна. У графика есть оси/единицы, подписи и доступная текстовая альтернатива. `null` разрывает линию, ноль остаётся нулём. Для partial показывать «Сумма доступных значений» и заметное пояснение; для no_data — «Нет данных», не 0.

«Аналитика» использует тот же `ForecastContext`, расширенный график и полную таблицу; повторный отдельный запрос из-за навигации не нужен. Не вводить KPI, процент заполнения вагонов, «рекомендуем добавить N вагонов» или сравнение с нормой без источника.

### 5.3. Таймлайн

Сохранить существующие выбор точки, range и проигрывание. Подпись содержит выбранный час/дату, значение и МСК; часовой и дневной шаги отображаются корректно. После ручного выбора проигрывание останавливается, как в действующей логике. При отсутствии точек и загрузке нового среза действия недоступны; после последней точки — понятное завершение.

Range работает клавиатурой и имеет осмысленный `aria-valuetext`, без буквального `null`. Проигрывание выбирает точки существующего ряда, не создаёт новые прогнозы и не имитирует движение трамвая. Окраску линий по загрузке оно не меняет, пока не существует проверенной геопривязки данных.

### 5.4. «О данных» и сообщения

Текущее окно «Настройки» преобразовать в «О данных», сохранив сведения о пакете, run, model, checksum, импорте, предупреждениях и ограничениях. Тема доступна напрямую в шапке. Технические ID показывать по раскрытию с переносом длинных строк; не занимать ими главный экран.

Видимый краткий статус: исторический режим, доступность пакета, покрытие и существенные ограничения. Полные предупреждения остаются достижимы. «Импортирован» не переименовывать в «Прогноз обновлён/модель обучена»: API не гарантирует дату обучения.

Состояния для карточки и аналитики: начальная загрузка; ready; partial; no_data; неподдержанный период; backend недоступен; ошибка/таймаут; экспорт идёт; конфликт CSV; устаревший run. Ошибки видны независимо от выбранной вкладки. При смене фильтра старые цифры не появляются под новым заголовком. Уведомления не смещают карту неожиданно и не перекрывают кнопки.

Для приёмки сравнить одинаковые фрагменты до/после с PDF: общий обзор, Чистые пруды, северо-восточные параллельные линии, северо-западный узел, южные окончания. ### 6.3. Взаимодействия и связь с прогнозом

Сохранить pan/zoom, колесо, pinch, кнопки и клавиатуру. Поиск ближайшей линии по геометрии уже реализован — довести его, не описывать как полностью новую функцию. Толщина hit-области определяется в экранных px; при неоднозначном касании параллельных линий дать компактный выбор кандидатов. Drag/pinch не должен завершаться случайным выбором. Нужен доступный способ выбрать ту же линию без точного попадания мышью.

Кнопки масштаба и закрытия полноэкранной карты минимум 44 × 44 px. Жесты на карте не должны перехватывать прокрутку всей карточки; явно разделить интерактивную поверхность и панели. После изменения размеров контейнера сохранить выбранную область карты, не применяя стартовый вид заново.

Карта 2026 года и прогнозные данные 2025 года не имеют автоматически подтверждённого соответствия. Номер/цвет/OCR недостаточны для связи. В базовой поставке сохранить независимое выделение карты и прогнозный селектор с краткой понятной пометкой об ограничении.

Если Игорь предоставляет проверенное соответствие, внедрить явный mapping `forecast route ID ↔ diagram route ↔ lane IDs` с источником и периодом применимости, согласовав формат с владельцем. Тогда выбор прогнозного маршрута подсвечивает подтверждённые линии; выбор линии с несколькими маршрутами предлагает список. Для неподтверждённой линии прогноз не подставляется. Такой mapping не должен содержать реальные валидации или секреты.

**До проверенного mapping не заявлять, что карта показывает динамическую загрузку.** Отсутствие mapping не блокирует темы, новую компоновку и улучшение геометрии; оно остаётся явно отмеченным функциональным ограничением.

### 7.2. Неприкосновенные инварианты данных

1. Запуск: `ready → capabilities → query`; единый закреплённый `forecast_run_id`.
2. Только относительные `/api/v2/handoff/*`. Сохранить Vite/Caddy proxy и текущие настройки окружения. Не прописывать production URL или Docker hostname в браузерный код.
3. `query` даёт общий результат для итога, графика, таблицы и CSV. Не рассчитывать альтернативный итог из округлённых UI-значений.
4. Экспорт использует `response.filters`, текущий run и `expected_result_id`; полная точность, null как отсутствие значения. Диспетчерский CSV не заменяет конкурсный submission.
5. Время МСК, границы `[start,end)`, сутки/неделя/календарный месяц по действующим функциям. Даты не сдвигаются в браузере с другой timezone.
6. Смена фильтров отменяет/отбрасывает старый ответ; CSV недоступен до нового корректного результата. Тема и вкладки не меняют filters/result.
7. `partial`, `no_data`, нули и baseline № 5 различаются. Никакой подстановки synthetic при сбое реального API.
8. HTTP 409 — повторить query перед CSV; 410 — обновить доступный run; 503/таймаут/сеть — явная недоступность и повтор. Сохранить обработку остальных ошибок в `handoff.ts`. Чтение 10 s, CSV 30 s, если контракт не изменён отдельно.
9. Предупреждения/ограничения не теряются при реорганизации карточки. Дневные интервалы не вычисляются суммой почасовых квантилей; новые интервалы не придумываются.
10. Сбой загрузки карты не уничтожает готовый прогноз/таблицу/CSV. При отсутствующем подготовленном артефакте проверка сборки карты остаётся обязательной.

Не использовать предложенный `openapi-v2-draft.json` вместо реально работающего handoff. Для новых полей/операций сначала согласовать принимающий контракт с Толей; данные географии — с Игорем; ML-сценарии — с Георгием; UI — с Артёмом. Пока ответа нет, выполнить независимые пункты этого ТЗ.

- [ ] Нет случайного horizontal overflow, обрезанного текста, недоступных кнопок, размытого текста или отсутствующей кириллицы.
- [ ] Контрольные фрагменты карты сравниваются с исходным PDF; raster из эскиза не попал в runtime вместо вектора.
- [ ] Скриншоты не используются как доказательство функции; интерактивность проверена отдельно.

Для сравнения композиции использовать одинаковые viewport и фиксированные разрешённые тестовые данные. Различие рабочих чисел с Figma нормально. Безопасные screenshots/fixtures можно приложить к отчёту; реальные данные не добавлять в Git.

```sh
npm ci --prefix frontend
npm run check:map --prefix frontend
npm run build --prefix frontend

NODE_PATH="$PWD/frontend/node_modules" QA_BROWSER=chromium python tests/frontend/run_browser.py
```

Python должен использовать окружение с `backend/requirements.txt`. Синтетический QA проверяет интерфейс/контракт, не качество модели. Сохранить успешные базовые проверки и запустить необходимые дополнительные проверки по изменённым слоям. Chrome/Chromium — автоматизированный проход; отдельно проверить мобильные жесты/нативные поля в доступном WebKit/Safari либо указать этот предел проверки.

### 11.3. Что считается готовым

Реализация принимается, когда одновременно выполнены компоновка C, обе темы, адаптивность, карта по проверенному реестру, сохранение работающих функций/API/CSV и необходимые проверки. Одного успешного build или статической страницы недостаточно.

Передать: изменённый существующий frontend; токены/шрифты с происхождением; подготовленные файлы карты и реестр исправлений; актуальные инструкции; отчёт с командами, результатами, обеими темами и размерами; остаточные ограничения с владельцами. Нельзя писать «все требования организаторов закрыты», пока зависимые функции из §8 не подтверждены.
