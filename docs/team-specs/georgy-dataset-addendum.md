Посадки в определении задачи не равны уникальным пассажирам или заполненности салона. `place_id` — площадка/депо, не остановка; `pass_route` не использовать как источник номера маршрута. Не вводить дополнительный фильтр `tran_type_id == 52` без основания: определение цели требует успешной валидации, а не только этого типа транзакции.

Проверить labels: ключи, типы, суммы, границы дат, дубли и отсутствие часов. По доступной части сырых данных проверить соответствие агрегации определению цели. Отсутствующий исторический ключ не превращать автоматически в ноль: определить, является ли это разреженной записью нулевых счётчиков или неполной выгрузкой. Для submission все ключи обязательны независимо от исторической наблюдаемости.

В файлах есть суточные хвосты. Разбивать по времени события: не включать сентябрь в обучение до 31 августа, ноябрь — в финальную историю до 31 октября. Проверить пересечение файлов и дубли событий на стыках; не удалять похожие оплаты без подтверждённого ключа. Часовой пояс исходных наивных дат явно установить в паспорте; не считать, что README документирует зону, если это не указано. Преобразование в принятую в продукте МСК должно быть воспроизводимым.

## 3. Первая обязательная поставка: прогноз всех 61 суток

1. Получить воспроизводимый сезонный baseline и полный конкурсный файл до расширения числа источников.
2. Основная локальная проверка: обучиться на январе–августе и из одной точки отсечения спрогнозировать весь сентябрь–октябрь. Это также 61 день.
3. Внутри проверяемого периода не подставлять реальные значения пассажиропотока предыдущих часов/дней. Backtest должен повторять финальный режим.
4. Сравнить baseline с выбранной ML-моделью. Рекурсия разрешена, но не обязательна; допустим прямой прогноз по доступным признакам и историческим профилям.
5. Для каждого лага и rolling-признака проверить доступность на всех горизонтах. За границей известного y использовать предусмотренную моделью схему, а не факты validation.
6. Если сентябрь–октябрь используется для настройки, называть его validation. По возможности проверить решение на более ранних последовательных окнах. Осенняя проверка не гарантирует такое же качество в декабре.
7. После выбора решения переобучиться на январе–октябре, выпустить прогноз ноября–декабря.

Считать общий score по общей сумме ошибок и фактов, не усреднять score маршрутов. При нулевой сумме фактов в локальном срезе — `score=null`, MAE и число строк отдельно. Отчёт: общий score/MAE, по маршрутам, пикам, рабочим/нерабочим дням и дальности прогноза; отдельно дни 1–7, 8–30, 31–61 и редкий маршрут 5. Baseline около 0.48 в README — результат организаторов, не наш замер.

## 4. Два режима внешней информации

**Конкурсный ретроспективный режим.** По ответу в ТГ разрешены внешние данные, опубликованные после 31.10.2025: фактическая погода, новости и другие допустимые внешние источники. Можно строить признаки целевого периода из таких источников. Будущий целевой пассажиропоток и скрытый эталон остаются недоступными; разрешение на внешние данные не является разрешением на получение ground truth.

**Эксплуатационный режим.** Для реального выпуска прогноза действует доступность информации на момент расчёта: архивные прогнозные выпуски погоды, заранее объявленные события и расписания. Фактическая погода будущего часа сюда не попадает.

Разделить эксперименты, метаданные и заявления о качестве этих режимов. Не менять `available_at`, чтобы источник формально прошёл прежнюю проверку. Ограничение `available_at <= as_of` сохраняется для эксплуатационного режима; конкурсное исключение оформить явно только для разрешённых внешних факторов. Семантику `as_of`, границы истории y и режим внешних источников согласовать с Даниэлем и Толей, не добавляя молча несовместимые поля в API.

Исторический погодный реанализ — реконструкция погоды с использованием моделей и наблюдений; не называть его прямыми измерениями на каждой остановке. В локальной конкурсной проверке использовать такой же тип внешней информации, что и в финальном расчёте.

### 5.2. Географическая привязка

- Для временных факторов по возможности покрыть январь–декабрь 2025: обучение, validation и целевой период. Собирать только ноябрь–декабрь недостаточно для измерения эффекта.
- README подтверждает пересечение справочников с целевыми маршрутами только по `{1,5,7,11,12}`. Остальные маршруты остаются в модели и submission; для них географические признаки имеют статус неподтверждённых до восстановления геометрии.
- Сначала календарь и общегородская погода для всех 10 маршрутов; затем локальные признаки только там, где есть проверенное соответствие. Общегородскую погоду обозначать как общую аппроксимацию.
- Расстояния считать в метрах по географическим координатам/подходящей проекции. PDF-пиксели карты не использовать. Современную топологию не переносить автоматически на 2025 год.
- Для события связывать площадку с доступными остановками или подтверждённым маршрутом; хранить метод и уверенность связи. Кандидаты радиусов 500/1000 м и окна до/после события выбирать на обучении/validation, не по скрытому эталону.
- При неизвестном окончании мероприятия не выдумывать время разъезда. Допустима явно обозначенная оценка по типу события как гипотеза с отдельным флагом, проверяемая на validation.
- Дедуплицировать одно событие из нескольких источников. Посещаемость, вместимость и число публикаций — разные показатели. Число публикаций само по себе не мера пассажирского спроса.

## 6. Что означает «мониторить» и что передавать команде

Для конкурса первым делом собрать исторический архив. Текущие новости сентября 2026 не заменяют факторы ноября–декабря 2025. Будущее оперативное обновление — отдельный режим продукта. Этот документ задаёт его проект; автоматические сборщики и расписания сейчас не создаются.

### Реестр источников

Для каждой из 16 групп оформить хотя бы один проверенный кандидат либо обоснованную недоступность. Предлагаемые внутренние поля реестра (не новый HTTP-контракт):

- `factor_id`, `source_id`, владелец, URL, способ получения, условия использования, необходимость ключа;
- период, география, временная детализация, доля покрытых часов/маршрутов отдельно для train/validation/forecast;
- `candidate / available / integrated / validated / rejected`; причина блокировки отдельно;
- `model_feature / context_only / scenario_only` и поддерживаемый режим информации;
- время последней успешной проверки, следующая проверка, ошибки/пробелы, актуальная версия snapshot и checksum;
- связанный `experiment_id`, изменение score/MAE и решение о включении.

`available` означает полученный и проверенный образец нужного периода, а не открывшуюся главную страницу. `integrated` — воспроизводимый признак с проверенным join. `validated` — задокументированная проверка эффекта, а не гарантированное улучшение; при отсутствии пользы фиксировать отклонение от включения и причину.

### Нормализованная запись события/фактора

Сохранять `source_url`, исходный ID, категорию, геометрию/адрес, время действия, время публикации и доступности (если известны), время получения, версию, качество, связь с маршрутами и правило преобразования в признаки. Неизвестные времена не заполнять выдуманными датами. Для статических объектов хранить период актуальности; для погоды — модель/станцию, единицы и интервал измерения/агрегации.

Сырой snapshot и нормализованные данные хранить локально вне Git. Преобразование в признаки воспроизводится без сети. HTTP-запрос пользователя не запускает скачивание и обучение. Источник может быть «нет событий» только при проверенном покрытии; ошибка получения или отсутствие архива — неизвестность, не ноль.

### Предлагаемая частота будущего оперативного обновления

| Группа | Частота-кандидат | Обработка сбоя |
|---|---|---|
| Календарь, учебные графики, статические объекты | При новой версии; периодическая проверка раз в неделю/месяц по типу источника | Сохранять версию и период актуальности |
| Погода | Примерно раз в час либо по выпуску модели | Возраст данных, обученный fallback, без подстановки «сухо» |
| Афиши, спорт, фестивали | Раз в сутки, перед событием повторная проверка отмены/переноса | Пометка неполного покрытия/устаревания |
| Плановые транспортные изменения | Каждые 3–6 часов при разрешённой частоте | Предыдущая версия только с явным статусом |
| Оперативные сбои/пробки | 5–15 минут только при подходящем API, квоте и реальной необходимости | Ограничение числа повторов, отсутствие сигнала не равно отсутствию сбоя |

Это ориентиры для согласования с лимитами источников, не обещание реализованного SLA. Для исторического конкурса вместо постоянного опроса достаточно версионированных снимков и повторной проверки исправлений.

## 7. Порядок внедрения и доказательство пользы

1. **P0:** аудит labels/границ → baseline → валидный файл → календарь 2025 → сопоставимая историческая погода.
2. **P1:** параллельно по смыслу вести реестр всех групп; по очереди проверять световой день, учебные календари, спортивные/культурные события, изменения трамвая и пересадочного транспорта, статические точки притяжения. Распределение работ согласовать с Игорем; это не поручение создавать дополнительных агентов.
3. **P2:** трафик, железнодорожные волны, торговые режимы, тарифы и редкие ограничения после проверки архива. На первичную проверку трудного источника — ориентир 30 минут; затем зафиксировать блокер и продолжить доступные группы.
4. Добавлять группы по одной при одинаковом разбиении и покрытии целевых строк. В итоговой комбинации по возможности убрать каждую группу отдельно, чтобы проверить её дополнительный вклад.
5. Проверять train/validation/forecast coverage, число строк до/после join, пропуски, стабильность схемы и возможность воспроизведения.
6. При пользе только на отдельных маршрутах/часах так и написать. Не складывать приросты разных экспериментов, не трактовать корреляцию или SHAP как доказанную причину.
7. Источник без сопоставимого исторического покрытия можно оставить контекстом или сценарием. Не добавлять ручной «+20% за концерт» в основной прогноз без локально проверенного основания.

Таблица экспериментов: версии данных/модели/факторов, seed и параметры, режим информации, границы обучения и проверки, группа признаков, покрытие, общий score/MAE, ключевые срезы, время расчёта, решение. Собственный baseline и каждая опубликованная цифра должны воспроизводиться.

## 8. Submission, продукт и совместимость

Конкурсный файл: ровно `route;date;hour;prediction`, без индекса. Проверить точное множество 14 640 ключей, отсутствие дублей/лишних строк, типы, даты, часы 0–23 и конечные неотрицательные числа. Взять ключи и порядок из `test_submission.csv`, заменив прогнозы; baseline-колонка шаблона не является y.

README говорит об округлении к целому, но не уточняет сторону и правило округления. Сохранить точность внутри модели, зафиксировать экспортное правило и сверить требования платформы. В отчёте учитывать ту обработку, которую реально применяет отправка.

Диспетчерский CSV из общего контракта — другой формат. Сценарные пользовательские коэффициенты в DS-файл не включать. Один почасовой run должен давать согласованные дневные и месячные суммы. Просмотр следующих 30 дней не заменяет прогноз всех 61 суток. Годовой сценарий и остановочная детализация не задерживают основной результат.

По ответу в ТГ лидерборд оценивает весь ноябрь–декабрь, отдельной скрытой части лидерборда нет, сохраняется лучший результат. При этом сам ground truth скрыт от участников. Вести журнал отправок: версия, checksum файла, параметры и score. Многократный подбор по лидерборду не подменяет локальную проверку.

Действующие `predict_mock()` и API v1 сохранить до согласованной миграции. Перед передачей проверить актуальный backend draft, если Толя уже изменил его: это дополнение не фиксирует неизвестную совместимость.
