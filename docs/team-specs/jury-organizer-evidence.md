## 2. Официальная шкала

### K1 Качество прогноза — 0–10

`WAPE-score = max(0, 1 − Σ|y − prediction| / Σy)`, больше — лучше. PDF, стр. 4; DATA, § 7. Это глобальное отношение сумм на оценочных строках, не среднее процентов по маршрутам.

| WAPE-score по таблице PDF | Исходный балл | С весом 2 |
|---|---:|---:|
| ≤ 0,48 | 0 | 0 |
| 0,48–0,60 | 1 | 2 |
| 0,60–0,70 | 2 | 4 |
| 0,70–0,80 | 3 | 6 |
| 0,80–0,88 | 4 | 8 |
| > 0,88 | 5 | 10 |

Диапазоны воспроизведены как в PDF; общие границы 0,60/0,70/0,80 отдельно не разъяснены. Порог максимума задан однозначно: строго >0,88. Ориентир baseline ≈0,48. Правило для случая нулевого знаменателя всей выборки в приведённом тексте не установлено; не придумывать его как официальное.

Q1 00:58–01:30: эксперт связывает более высокое качество с преимуществом. CHAT-2: score остаётся одним из инструментов оценки. Из этого нельзя вывести точную дополнительную формулу баллов или тай-брейка после 0,88.

| Подкритерий | Максимум | Условие |
|---|---:|---|
| Трафик/загруженность улиц | 1 | Источник использован, эффект подтверждён, дана рабочая ссылка/способ получения |

Источник без ссылки не засчитывается по тексту PDF. Список потенциальных источников не равен их использованию. «Чем больше факторов, тем лучше» — пожелание исследовать возможности, а не доказательство прироста качества от каждого признака.

### K3 Архитектура и производительность — 0–5

PDF, стр. 2–3 и 5:

- Запускаемый через Docker контейнеризированный backend + frontend, REST/HTTP API, интерактивный дашборд и табличная выгрузка.
- Читаемое разделение: приём/нормализация → признаки/геопривязка → ML/агрегация → API → UI; общие архитектурные принципы.
- API по параметрам маршрута, остановки/участка, интервала и горизонта; детализацию сопоставлять с уточнениями DATA.
- Ориентир нагрузки: один контейнер, 2–4 vCPU / 2–4 ГБ RAM, сотни RPS, p95 <200–300 мс, CPU 60–80% с запасом, стабильная память без swap. CPU ниже ориентира сам по себе не является дефектом эффективности.
- **Результаты измерений обязательно привести в README.** На стр. 5 сказано, что отдельный нагрузочный тест жюри не проводит; честная оценка с подтверждением засчитывается. Нельзя выдавать характеристики тарифа VPS за измерения.
- Горизонтальное масштабирование, эффективное использование ресурсов, понятная обработка API-ошибок, расширение за счёт погоды, транспорта, строительства/новых маршрутов.
- Отсутствие запускаемого сервиса существенно снижает балл. Точной формулы распределения пяти баллов по подпунктам нет.

Рекомендованы Java 17+/Spring/Netty, React/TypeScript, Python ML, Docker/Compose, хранилище и картографическая библиотека. SLIDES отдельно уточняет необязательность backend-стека. Переписывать FastAPI ради формального соответствия Java не требуется. Рекомендованные роли команды не являются отдельными критериями.

### K4 Полнота функциональности — 0–4

PDF, стр. 1–2 и 5:

- День с почасовой детализацией, месяц, год. На стр. 1 год опционален; на стр. 5 день обязателен, месяц и год допускаются хотя бы качественно. Для максимума нужно оценить годовой сценарий; точная численная модель на год не установлена безусловным требованием.
- Фильтрация/агрегация по маршруту, остановке/участку и интервалу.
- Карта Москвы с динамикой пассажиропотока во времени и точках маршрута, удобный интерактивный дашборд.
- Экспорт CSV и/или XLSX: работающего CSV достаточно для формата, XLSX не обязателен.
- Учитывать время суток, день недели, сезонность и погоду при наличии данных.

DATA, § 4, уточняет: основная метрика — маршрут × час, остановочная детализация — необязательный бонус из-за ограниченных справочников. Нельзя объявлять отсутствие модели по остановкам дисквалификацией или делать вид, что отображение остановок уже является остановочным прогнозом. Точного перераспределения четырёх баллов после этого уточнения нет.

Слова PDF о визуализации «в реальном времени» сопоставляются с историческим прогнозным периодом DATA: интерактивное обновление представления не доказывает живой поток телематики сегодняшнего дня.

### K5 Бизнес-ценность — 0–2

PDF, стр. 1 и 5: применение для распределения подвижного состава, снижения переполнения, уточнения расписаний и оптимизации эксплуатации. Важны реалистичные выводы и понимание ограничений. Целевой пользователь — диспетчер ЕДЦ/трамвайного управления. Из количества посадок нельзя без дополнительных данных получить заполненность конкретного вагона.

Дополнительные особенности DATA: `tran_no` — ID транзакции, `device_no` — валидатор, `begin_date_time` — служебное начало поездки, `good_type` — тариф, `bus_exit_no` — выход/график ТС, `garage_number` — бортовой номер. Не использовать тариф/пересадку как основание исключить успешную посадку. Схемы организаторов не дополнять вымышленными полями высадки, вместимости или stop_id события.

CHAT-1, переслан 25.09:

- Прогнозный период именно ноябрь–декабрь, не октябрь–ноябрь; одна непрерывная сетка, а не прогноз с ежедневной подстановкой неизвестного факта.

Даниэль передал это как разъяснение организаторов; исходная роль автора/ссылка не проверены независимо.
- Отсутствие отдельного скрытого пересчёта leaderboard не означает доступность скрытого ground truth. Ответа на последующий вопрос участника о «математическом score 1» в предоставленном фрагменте нет; из самого вопроса правило не выводится.

CHAT-2 имеет более поздний приоритет по № 5: формат и таймстемпы выданного sample подтверждены; нули № 5 допустимы, назван теоретический потолок **0,9935**. Это не score команды, не поправка +0,0065 к любому локальному результату и не основание выкинуть № 5. Прежняя трактовка «13 176 строк на сдачу» отменена в [письменной поправке](../integration/qa-2026-09-25/submission-clarification.md).

Правило `floor(x + 0.5)` — принятая реализация команды для неотрицательных чисел; поведение ровно на x,5 не сформулировано отдельно организаторами. Внутренние float, HTTP-границы `[start,end)`, Europe/Moscow и формат диспетчерского экспорта — действующие командные контракты, не дословные требования CSV. Исходная временная зона raw ещё требует подтверждения; не выполнять скрытую конвертацию.
