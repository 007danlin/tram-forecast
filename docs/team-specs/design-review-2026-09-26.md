# TramFlow: основания для ТЗ на редизайн

26 сентября 2026. **Исследование; не описание реализованного редизайна.** После исследования Даниэль выбрал C «Вечерняя смена» с переключением тёмной/светлой темы. Актуальное задание: [ТЗ для Codex](codex-evening-shift-redesign.md). Предварительные предложения ниже читать с учётом выбранного направления и уточнений ТЗ.

Цель Даниэля: минималистичный, выразительный интерфейс в духе Московского транспорта; аккуратно довести интерактивную трамвайную схему; сохранить работающие функции и доказательства для критериев организаторов; адаптировать продукт к компьютеру и телефону.

## 2. Источники требований

Прочитан локальный первоисточник организаторов: `~/Downloads/ИИ-прогноз загрузки трамвайных маршрутов.pdf`, 6 страниц. Название файловой системы содержит составные Unicode-символы; искать по префиксу `ИИ-прогноз`. Страницы 1–3 — задача и требования, 3–5 — оценка, 6 — артефакты и питч.

Дополнительно прочитаны `docs/team-specs/qa-2026-09-25/artem.md`, `acceptance.md`, актуальные frontend README и INTEGRATION из проверенного снимка main. Q&A в документации является зафиксированной командой интерпретацией; видеозапись в этой работе не переслушивалась. Закрытая платформа организаторов и возможные новые объявления там не проверялись.

| Критерий из PDF | Максимум | Связь с редизайном |
|---|---:|---|
| Качество прогноза, WAPE-score | 10 | Оформление не улучшает score. Не менять ML, округление submission или установленный пакет в рамках визуальной задачи |
| Данные, внешние источники, применимость | 8 | Сохранить объяснение области применения и источников. Из этих 8: внешние источники до 4, применимость до 2, коэффициенты в UI +1 и корректная агрегация/пайплайн +1 |
| Архитектура и производительность | 5 | Сохранить запуск, API, разделение слоёв и подтверждённые замеры. Не ухудшить скорость карты и отзывчивость |
| Горизонты, агрегация, карта, экспорт | 4 | Прямой предмет функциональной приёмки интерфейса; видимость кнопки не доказывает выполнение функции |
| Бизнес-применимость | 2 | Быстрый переход к маршруту, понятный период, пик спроса, ограничения, передача результата |
| Полуфинальный питч | 10 | Читаемое демонстрационное представление помогает показать результат, но не гарантирует оценку |

Основной этап — максимум **29**, вместе с питчем — **39**. Оценка команды этим исследованием не устанавливается.

Годовой горизонт: на стр. 1 назван опциональным сценарием, на стр. 5 среди полноты функциональности указаны день/месяц/год, причём месяц и год хотя бы качественно. Поэтому нельзя считать отсутствующий год закрытым только отключённой кнопкой. Нужен отдельный согласованный качественный сценарий либо явное указание непокрытого пункта. Численный годовой ряд из текущего API не следует.

CSV **или** XLSX удовлетворяют формулировке экспорта; XLSX не обязателен при корректном CSV. Неделя добавлена по командной фиксации Q&A и уже работает — её сохраняем.

## 3. Что сейчас работает и что ещё не закрыто

На сервере есть полноэкранная SVG-схема, плавающие фильтры, карточка слева, таймлайн, раздел аналитики, окно сведений/настроек. Поиск ближайшей линии уже использует геометрию; не предлагать внедрение этого алгоритма как отсутствующей функции. В исходниках имеется сохранение состояния карты при переключении представления.

| Область | Подтверждённое состояние | Требование к будущему ТЗ |
|---|---|---|
| Маршрут и период | Маршрут из capabilities, день/неделя/месяц, МСК | Сохранить; источник доступности — API |
| Прогноз | Итог, пик ряда, график, таблица, покрытие | Использовать один результат; не подменять числа ради композиции |
| CSV | Экспорт через handoff с закреплением результата | Сохранить filters/run/result и исходную точность |
| Карта | Pan/zoom/pinch, клавиатура, выделение линии | Сохранить и довести вид схемы; не заменить интерактивность картинкой |
| Карта ↔ прогноз | Независимы | Связать только через проверенное соответствие маршрутов и версий; не по цвету и не по одному OCR-номеру |
| Остановки/направления/участки | Недоступны; вкладка не даёт остановочного прогноза | Отдельная задача данных/API, не декоративные активные контролы |
| Коэффициенты | Кнопка сценария отключена | Для +1 по соответствующему подпункту нужна работающая согласованная база/сценарий, не только дизайн панели |
| Год | Отключён | Отдельный качественный сценарий с предположениями после согласования |
| Избранное, настройки | Звезда отключена; реализованных настроек нет | Убрать неработающую звезду; сведения о данных вынести в честно названный раздел |
| Сравнение с обычным уровнем | Нет данных | Не держать пустую метрику в главной сводке; вернуть при наличии подтверждённой базы |

Перечисленные функциональные пробелы уже существуют. Редизайн не должен маскировать их и не должен описываться как полное выполнение всех критериев.

## 4. Схема: что именно доводить

Локальный `trammap_15_04_26-2.pdf` совпал с SHA-256, записанным в `network.json`: `13bf11ade2d5a36bd3af8b4990e505e9692cf39eacbdb91f79e419f83bcf5c6f`. Визуально просмотрен исходный PDF. Референс соответствует 2026 году, прогнозный период UI — ноябрь–декабрь 2025. Совпадение номера маршрута не подтверждает историческую идентичность геометрии.

В сети: **45 линий**, **1 098 точек остановок**, **424 подписи**, **47 групп достопримечательностей**, **58 значков метро**. Это элементы рисунка, не количество уникальных транспортных сущностей. **9 линий** помечены `inferred`, у **5 точек** нет label. Этот аудит не утверждает, что все остальные подписи правильные.

В исходной схеме есть река, парки, дороги, пересадочный контекст и более тщательно свёрстанные подписи. В действующем рендерере переносится часть слоёв; фон — заливка. Предыдущая попытка нарисовать произвольную городскую подложку отклонена, что отражено в актуальном frontend README.

Для будущего ТЗ:

1. Сохранить геометрию Артёма и цвета маршрутов как основу. Проверить стыки, разрывы, параллельные линии, пересечения, окончания и номера по точному PDF, а не перерисовывать приблизительно.
2. Составить перечень расхождений с координатами/ID; отдельно проверить 9 inferred-линий и 5 точек без label. Сверить OCR на выбранных контрольных фрагментах, потом пройти оставшиеся спорные места.
3. Восстановить нужные фоновые слои из **этого же** референса в той же системе координат. Не придумывать русло, парки и улицы, не накладывать произвольные географические тайлы на схематическую геометрию.
4. Разделить фон, линии, остановки, подписи, номера, достопримечательности, пересадки, hit-области и выделение. Контекст должен помогать ориентироваться, не конкурируя с выбранным маршрутом.
5. Исправлять толщины, зазоры и текст по масштабу. `textLength` не должен давать заметно растянутые буквы. Проверять подписи на рабочем масштабе; на общем обзоре применять уровни детализации.
6. Цвет маршрута — идентичность, не загрузка. Для спроса нужен отдельный слой/маркер и легенда только при наличии геопривязанных значений.
7. Touch hit-области считать в экранных пикселях. При неоднозначности соседних линий предлагать выбор; drag/pinch не должны превращаться в случайный клик. Выбор доступен также через список с клавиатуры.
8. Не сбрасывать pan/zoom при запросе, смене графика/таблицы, открытии панели или возвращении из аналитики. Добавление «Вся схема» не должно молча менять смысл существующей кнопки «Исходный вид».
9. Сопоставление `forecast route ID ↔ diagram route ↔ lane IDs` хранить явно и проверяемо с датами применимости и источником. Номер, общий цвет, близость и OCR сами по себе недостаточны. Неподтверждённый объект остаётся без прогноза.
10. Уточнение пользователя в этой задаче снимает **для нового редизайна** прежний запрет на правку карты из `artem-ui-layout.md`; несовместимые API-контракты по-прежнему согласуются с владельцами.

Подтверждено по части 3:

- § 3.2.3, PDF-страница 14 (печатная 27): основной красный **RGB 228 / 0 / 13 = #E4000D**, белый фон; нейтральный серый **RGB 175 / 173 / 172 = #AFADAC**. Красный на белом и белый на красном — базовая пара. Дополнительные печатные цвета не переносятся автоматически в интерфейс.
- § 3.2.4, PDF-страница 15 (печатные 28–29): **Moscow Sans**, Regular для основного текста, ExtraBold преимущественно для заголовков. В архиве присутствуют соответствующие OTF-файлы. Правило двух начертаний сформулировано для печати; веб-токены и размеры требуют отдельной разработки.
- § 3.2.2: фирменный узор имеет ограничения применения; его не следует добавлять декоративным фоном веб-панелей.
- Логотипы следует брать из исходных файлов, не рисовать похожий знак. Эскизный знак TramFlow не является логотипом Московского транспорта.

Архив МГТ не прочитан; остальные перечисленные пользователем архивы и отдельный пакет Fonts не объявляются изученными. Для выбранной концепции основой служит материнский бренд МТ, а не смесь цветов разных транспортных служб. Доступность OTF в архиве не подменяет проверку условий веб-встраивания при реализации.

Прочитаны первичные страницы Студии Лебедева:

## 6. Общие для любого варианта правила реализации

- Основной экран отвечает на четыре вопроса: какой маршрут, какой период, сколько успешных посадок, когда пик. Вторичные сведения — по раскрытию.
- Сохранить работоспособные представления «Карта», «Карта и прогноз», «Аналитика» с одним состоянием фильтров. Трёх готовых компоновок достаточно; свободный конструктор панелей не нужен.
- Не уменьшать desktop пропорционально до телефона. На мобильном — компактный контекст, карта и раскрываемая панель/отдельное представление аналитики; фильтры открываются отдельно. Кнопки и существенная информация доступны без hover.
- Предлагаемая проверочная сетка: 360×800, 390×844, 768×1024, 1024×768, 1366×768, 1440×900. Это критерии команды, не цитата из PDF. При увеличении текста до 200% не терять действия и сообщения.
- Одна заметная основная кнопка на контекст; вторичные действия нейтральные. Единые иконки без emoji и неодинаковых растровых значков. Минимальная touch-область 44×44 px.
- Покрытие, historical-режим, baseline № 5, partial/no_data и ограничения должны быть понятны, но технический run/checksum не нужен постоянно поверх карты.
- Смысл метрики — успешные посадки/валидации, не число уникальных людей и не процент заполнения вагонов. «Добавить N вагонов» нельзя рассчитывать без вместимости, выпуска и дополнительных данных.
- `ready → capabilities → query`, единый result, отмена устаревших ответов, исходная точность CSV, МСК и ошибки 409/410/503 сохраняются.
- Не заменять пропуски нулями, не соединять null на графике, не показывать новый контекст поверх старого результата. Ошибка видна независимо от вкладки карточки.
- Сценарные коэффициенты, остановочная агрегация и год — отдельный согласованный этап. Не реализовывать новые формулы во frontend и не создавать фиктивный API.
- Карта грузится отдельно от forecast-состояний; панели и жесты не блокируют друг друга. При сбое карты график/таблица/экспорт остаются доступны, если данные готовы.
- Набор существующих `tests/frontend/handoff.cjs` и `run_browser.py` сохранить, адаптируя селекторы к новым доступным названиям. Дополнить только содержательными проверками новых жестов, адаптивности и согласованного mapping.
- Для карты снять одинаковые контрольные фрагменты до/после, сравнить с PDF: общий вид, Чистые пруды, северо-восточные параллельные линии, северо-западный узел, южные окончания. Не объявлять совпадение по одному удачному фрагменту.
- При реализации обновить frontend README и INTEGRATION в том же PR, разделяя готовое и будущее. Не менять лицензию, ML-данные, секреты; commit/push/публикация — только по отдельной просьбе.

## 7. Итог выбора

Даниэль выбрал C и попросил сохранить его внешний вид, добавить переключатель тем и светлую палитру Московского транспорта. Подготовлено [исполнимое ТЗ для Codex](codex-evening-shift-redesign.md): точные фреймы, сетка, две темы, компоненты, работа с картой, интеграционные инварианты и приёмка. Для совпадения с выбранным эскизом ТЗ фиксирует Manrope, уточняя предварительное предложение о Moscow Sans. Реализация и публикация этим исследованием не выполнялись.
