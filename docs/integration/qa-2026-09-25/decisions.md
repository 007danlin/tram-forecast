## QA-01 sample, область модели и интерфейс

[Письменное уточнение и исправление прежнего вывода](submission-clarification.md)
имеют приоритет над трактовкой устного Q&A. Сдаём полный исходный sample;
№ 5 и ночные таймстемпы не удаляем. В аудите Георгия указаны 14 640 строк и
десять маршрутов; Игорь ещё должен сверить фактический файл и checksum.
Нулевой fallback № 5 допустим с потерей по метрике: организаторы назвали потолок
0,9935 при идеальном прогнозе остальных маршрутов, а не качество нашей модели.

Обучение при недостатке истории, fallback конкурсного экспорта и capabilities
API описываются отдельно. Общий локальный score включает весь оценочный набор;
срез по девяти маршрутам не подменяет общую метрику. В продукте fallback не выдаётся
за обученную модель или подтверждённое отсутствие движения. Возможности API/UI
принимаются владельцами по реальным артефактам; карта этим уточнением не меняется.

Игорь сверяет версию/хеш исходного sample, строки и уникальные ключи, порядок,
таймстемпы, дубли/пропуски и № 5. Ждать нового sample без № 5 не требуется.

## QA-02 рабочее время и частичный час

Иллюстративное расписание `[05:30, 01:00 следующего дня)` не является общим
расписанием маршрутов. Если оно подтверждено для конкретного маршрута и даты,
событие в 05:29 исключается из train, 05:30 включается; ровно 01:00 не входит.
Бин `[05:00,06:00)` содержит только допустимые события `[05:30,06:00)`.
Не умножаем полученную сумму на два. Если доступны лишь часовые агрегаты,
не можем восстановить половину часа без дополнительных данных: фиксируем
неопределённость, согласуем правило с Игорем/Георгием.

Ночной ключ из sample сохраняется. Его наличие не разрешает автоматически ставить
ноль; исключение из обучения не определяет маску метрики. Ноль/no_service требует
основания в расписании и принятого правила. Пропуск связи не становится нулём.

## QA-03 округление и два экспорта

Синтетические примеры для принятия, не результаты модели:

| Вход / действие | Предлагаемый DS-результат | Что проверяет |
|---|---|---|
| 2.49; 2.50; 2.51; 3.50 | 2; 3; 3; 4 | Ближайшее целое, x,5 вверх; Python round не заменяет это правило |
| Две части одного ключа: 0.49 + 0.49 | 0.98 → 1 | Сначала сумма до зерна sample, потом округление; не 0 + 0 |
| Два разных часовых ключа: 0.49 и 0.49 | 0 и 0 в DS | Дневная сумма DS равна 0; округлённая сумма внутреннего прогноза может быть 1 |
| Пропуск, NaN, бесконечность, отрицательное значение | Остановить экспорт и передать на проверку | Валидация не подменяется нулём; clipping возможен только как отдельно принятая и проверенная постобработка |

Предложение для диспетчерского контура: API и CSV сохраняют одинаковые точные числа
и result_id; UI округляет только представление, явно обозначая это. Итог считается
по исходным значениям, не по округлённым ячейкам. Экран/CSV сверяются на исходной
точности; при показе целых итог может отличаться от суммы видимых округлённых ячеек.
Если владельцы выберут целочисленные API/CSV, сначала нужен единый альтернативный
пример сохранения сумм и версия контракта. DS-экспорт отдельный; его точное правило
постобработки включается в backtest и метрику Георгия. Ответ Q&A не меняет v1.

## QA-04 и QA-05 временные границы

Все интервалы `[start,end)`, часовой пояс Europe/Moscow. `end` не включается.
Времена с `+03:00`; UI показывает обе даты и шаг. Примеры задают семантику,
а не новые payload HTTP: draft `2.0-draft.1` не поддерживает неделю.

| Режим | Начало | Конец | Число интервалов |
|---|---|---|---|
| День, прежнее внутреннее определение | 2025-11-01 09:00 +03:00 | 2025-11-02 09:00 +03:00 | 24 часа |
| Неделя с выбранной даты, не ISO-неделя | 2025-11-28 00:00 +03:00 | 2025-12-05 00:00 +03:00 | 7 дней |
| Следующие 30 дней | 2025-11-28 00:00 +03:00 | 2025-12-28 00:00 +03:00 | 30 дней |
| Год, 12 календарных месяцев | 2027-11-01 00:00 +03:00 | 2028-11-01 00:00 +03:00 | 12 месяцев, 366 суток |
| Альтернатива 365 дней от той же даты | 2027-11-01 00:00 +03:00 | 2028-10-31 00:00 +03:00 | 365 дней; иной конец |

Произвольная дата 15 ноября не округляется молча к первому числу для года: UI
выбирает месяц, неподходящий запрос отклоняется по принятому будущему контракту.
Для дневного шага неполночные границы также не округляются молча.

Предлагаемые состояния долгого расчёта: ожидание → расчёт → готово либо ошибка.
Это названия состояний для обсуждения, не введённые endpoint/поля/брокер.
Дневной запрос продолжает читать прежний готовый run. UI сохраняет объект, даты
и выбранную компоновку, показывает режим/дату результата и отдельный статус расчёта.
При ошибке прежний run не выдаётся за новый; qualitative не содержит численного
прогноза. Приёмка Толи: запустить долгий расчёт, одновременно проверить дневной
query и записать задержку/ошибки/версии. Порог производительности принимается
по реальному замеру, а не назначается этим документом.
