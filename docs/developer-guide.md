# tram-forecast

> Технический справочник запуска и исторических проверок. Текущий конкурсный лидер — C01; актуальные версии и краткая инструкция находятся в [главном README](../README.md). Упоминания B2 как принятой модели ниже относятся к веб-комплекту.

Актуальная локальная доработка 27.09: [итоговая приёмка](submission-final/final-closure-status.md), [инструкция сдачи](submission-final/README.md). B2 и прежний интерфейс опубликованы; новые блоки проверки выпуска и годового плана этого этапа подготовлены локально.
TramFlow — AI Passenger Flow Forecasting

Сервис прогнозирования успешных посадок на трамвайных маршрутах. Frontend
показывает готовый проверенный ML-прогноз через FastAPI: день, неделю или месяц
и CSV того же результата. Обзор маршрутов, выбранное время и маршрутная панель
рядом с картой используют один прогноз; остановочные значения не оцениваются.
Принят исходный B2 (platform 0,84260). Качественный год содержит условные сценарии и план проверки на 12 месяцев; численного года нет. Ручные поправки: погода, мероприятия, перекрытия, изменения движения — четыре коэффициента 0,5–1,5 с шагом 0,05. Их произведение умножает базовый прогноз; сценарный CSV хранит базу и поправки отдельно.
Автоматический [мониторинг города](../backend/monitoring/README.md) показывает текущие снимки: они не меняют историческую модель и не доказывают эффект её признаков.

| Часть | Состояние |
|---|---|
| Frontend | Обзор → маршрут/время → график/таблица/панель у карты; онлайн-мониторинг источников, качественный год, закреплённый CSV; без ML-пакета — ошибка готовности |
| `/api/v2/handoff/*` | Чтение проверенного CSV, часовой/дневной срез и экспорт; нужен отдельно импортированный release |
| `/api/v1/*` | Сохранённый синтетический пример для совместимости и smoke-проверок |
| `python -m ml` | Обучение, оценка, batch, внешние факторы и submission; нужны ML-зависимости и локальный датасет |
| `ml/inference/Dockerfile` | Отдельный offline CLI для сохранённого B2; обучение и готовые ответы для inference не нужны |
| Общий API `2.0-draft.1` | Отдельное предложение для согласования; его операции не подключены к серверу |

Исходники и карта находятся в Git; датасет, веса, готовый прогноз и credentials
передаются отдельно. Для полного запуска с данными выполните раздел
«Подключить готовый ML-пакет» ниже. Поставка на VPS, сохранение release при обновлении
и переход после переписывания истории описаны в [deploy/release.md](../deploy/release.md).
Публикация кода в GitHub сама по себе не обновляет сервер.

## Получить и запустить

Нужны Git, Python 3.12 и Node.js 22.12+. Python 3.12 используется в CI и Docker;
для воспроизводимого ML-окружения используйте его же. Команды ниже для macOS/Linux.

```sh
git clone git@github.com:MISISion-Possible/tram-forecast.git
cd tram-forecast
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements.txt
python -m uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000
```

В другом терминале из корня репозитория:

```sh
cd frontend
npm ci
npm run dev
```

Откройте [страницу](http://localhost:5173). Без установленного ML-пакета видны
карта и сообщение о недоступности прогноза; график появится после импорта ниже.
Для запуска серверов переменные необязательны; `.env.example` настраивает только
адрес backend для Vite-прокси. Контракты и конфигурация описаны в
[INTEGRATION.md](../INTEGRATION.md), схема работающего API — в
[Swagger](http://localhost:8000/docs). `/docs` и `/openapi.json` доступны напрямую
на backend: frontend-прокси и серверный Caddy проксируют только `/api/*`.

Альтернатива с запущенным Docker Desktop / Docker Engine:

```sh
docker compose up --build
# Остановить и удалить контейнеры:
docker compose down
```

Адрес страницы тот же. Это локальная заготовка, контейнер frontend использует Vite preview.
Готовая карта поставляется в Git; PDF и OCR для запуска не нужны. Сборка проверяет
её комплектность. Подробнее — [frontend/README.md](../frontend/README.md).

## Подключить готовый ML-пакет

Архив передаётся отдельно и не появляется после `git clone`. Из корня, с
установленными backend-зависимостями, импортируйте совместимый пакет в **новый** каталог:

```sh
.venv/bin/python -m backend.handoff.install /absolute/path/tramflow-ml-handoff-v1.zip \
  --output artifacts/ml-handoff-v1
TRAMFLOW_HANDOFF_DIR="$PWD/artifacts/ml-handoff-v1" \
  .venv/bin/python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000
```

Этот запуск заменяет обычный backend на том же порту. Backend читает переменную
процесса; запись `TRAMFLOW_HANDOFF_DIR` только в `.env` сама по себе его не настроит.
После запуска в другом терминале:

```sh
curl --fail http://127.0.0.1:8000/api/v2/handoff/ready
.venv/bin/python -m backend.handoff.check \
  --base-url http://127.0.0.1:8000 --release artifacts/ml-handoff-v1
```

Для локального Docker вместо двух процессов:

```sh
export TRAMFLOW_HANDOFF_HOST_DIR="$PWD/artifacts/ml-handoff-v1"
docker compose -f compose.yaml -f compose.handoff.yaml up --build
# Остановка в другом терминале с той же переменной:
docker compose -f compose.yaml -f compose.handoff.yaml down
```

Пакет монтируется только для чтения. Обычный health/статус healthy проверяет v1,
поэтому handoff/ready проверяется отдельно. Сервер не исполняет модель из архива;
ML-библиотеки для выдачи CSV не нужны. Frontend использует handoff и показывает данные готового пакета; synthetic v1
не подставляется вместо отсутствующего прогноза.
Пакет исторический: ноябрь–декабрь 2025, 10 маршрутов, № 5 — нулевой baseline.
API поддерживает максимум 31 день за запрос; его CSV отличается от конкурсного submission.
Формат архива, запросы, ошибки и серверная установка — в
[инструкции handoff](../backend/handoff/README.md).

## Рассчитать B2 в Docker из сохранённых весов

[Полная инструкция](../ml/inference/README.md) содержит подготовку проверенных
model/sample, `docker build`, оба `docker run` и отдельное сравнение с эталоном.
Проверочный скрипт использует только стандартную библиотеку Python на хосте;
ML исполняется внутри Python 3.12.14 с точными pins и закреплённой базой.

```sh
docker build -f ml/inference/Dockerfile -t tramflow-inference:b2 .
python3 -m scripts.verify_container_inference --help
```

Два полных расчёта без сети/fit/готовых ответов побайтно воспроизвели принятый B2:
14 640 строк, прежние SHA float/submission, нулевой № 5, preflight passed.
Профиль 2 CPU / 4 GiB / swap 0: полный forecast `docker start --attach`
3,05–3,15 с, расчёт с загрузкой модели 1,37–1,40 с; измеренный пик RSS
для четырёх полных вызовов ≤184,39 MiB. Это локальные наблюдения ARM64,
не p95/RPS. На VPS Linux AMD64 отдельно прошли все 15 сценариев и точное
сравнение B2: полный forecast 10,75–11,26 с, пик RSS ≤186,80 MiB.
[Условия и оба протокола](submission-final/docker-inference-verification.md).
Обычный Compose по-прежнему выдаёт готовый handoff; inference запускается явно,
после расчёта новый float проходит существующие упаковщик и импортёр.
Соответствие неизвестному потоковому протоколу жюри этим не устанавливается.

## Автоматические проверки в GitHub

После каждого `git push` в любую ветку и при открытии/обновлении PR запускается [CI](https://github.com/MISISion-Possible/tram-forecast/actions/workflows/ci.yml):

- **Backend and ML tests** — комплектность поставки, контракты и handoff, сверка OpenAPI, интеграционные, ML и tooling-тесты; ML-проверки покрывают target, raw/rounded-метрики, календарь/погоду, реестр F01–F16, 61-дневные срезы, baseline, ансамбль, рекурсивный inference, QA-маску и submission preflight; также проверяются зависимости.
- **Frontend typecheck and build** — установка из lock-файла, проверка TypeScript и сборка страницы.
- **Compose smoke test** — сборка контейнеров, synthetic v1 и передача синтетического ML-пакета через read-only mount; API/CSV проверяются до и после остановки backend.

Локальный commit без push не запускает GitHub Actions. Результат виден во вкладке Actions и в PR: зелёный — проверки прошли, красный — откройте упавший шаг и его журнал.
Workflow можно запустить вручную через Actions → CI → Run workflow. Секреты и сторонние сервисы не нужны; деплоя нет.
Эти проверки находят поломки интеграции, но не повторяют обучение на реальных
данных. Контейнерный handoff проверяется на явно синтетическом пакете.
Браузерные проверки handoff — отдельный workflow и [frontend/README.md](../frontend/README.md).
Caddy-проверки описаны в [инструкции доступа](../deploy/access.md).

Для локального повтора backend/ML job установите оба набора зависимостей:

```sh
.venv/bin/python -m pip install -r backend/requirements.txt -r ml/requirements.txt
.venv/bin/python -m pip check
.venv/bin/python -m unittest discover -s backend/tests -v
.venv/bin/python -m backend.contracts.openapi --check
.venv/bin/python -m unittest discover -s tests/integration -v
.venv/bin/python -m unittest discover -s tests/ml -v
.venv/bin/python -m unittest discover -s tests/tooling -v
npm --prefix frontend run build
docker compose config --quiet
```

HTTP-тесты сами поднимают временные localhost-сервисы. Сборка и `compose config`
не заменяют запуск контейнеров и проверку страницы.

## Реальный ML batch

Инструкции, зависимости и команды находятся в [ml/README.md](../ml/README.md).
По отчёту Георгия потоковая проверка raw CSV воспроизвела labels без расхождений.
На ранних folds выбранный фиксированный calendar/interaction ensemble получил
rounded score 0.8505524 против 0.8400868 у прежней модели. На повторно
использованном 61-дневном validation-окне сентября–октября rounded score —
0.8290094 против 0.8231869 у previous-weekday.
Этот период уже оценивался в PR #2 с опубликованным raw score 0.8287 и не
является pristine holdout; в текущем run модель по нему не перевыбиралась.
Это результаты автора, не независимый повтор и не score платформы. ERA5 проверен отдельно в конкурсном ретро-режиме и не
вошёл в финальный operational-артефакт.
QA-дополнение 26 сентября ограничивает область обучаемой модели девятью
маршрутами без № 5. Локальный organizer sample при этом всё ещё содержит 10
маршрутов и 14 640 строк. Принят полный sample на 14 640 строк с нулевым № 5;
девятимаршрутный CSV используется только для диагностики. Подтверждённая маска технологических
валидаций от Игоря отсутствует, поэтому cleaned-model score не заявляется.
Детали и контрольные суммы — в [QA-отчёте](../ml/reports/qa-addendum-2026-09-26.md),
журнал улучшения — в [отчёте quality 0,85](../ml/reports/quality-improvement-2026-09-26.md).
`fetch-weather` получает исторический ERA5 snapshot, а `prepare-weather`
нормализует локальный JSON. Режимы и проверка источника описаны в ML-инструкции.
90%-й интервал недокалиброван: фактическое покрытие повторного validation-окна
0,8166 по паспорту модели.
Метрики относятся к `calendar-interaction-ensemble`; они не подтверждают качество произвольного
handoff-пакета без сверки его модели/версии. Текущий принятый handoff связан с исходным B2 через model/float/DS SHA; после слияния ML-кода модель автоматически не меняется. Итог v4/v4.1 — no_improvement по заданному правилу замены. [Приёмка ML и календарная абляция](submission-final/ml-closure-evidence.md).

Модель, оба submission-кандидата и реальные данные остаются локальными в игнорируемых Git
директориях. HTTP v1 сохраняет mock; frontend использует handoff. Отдельный
`/api/v2/handoff/*` обслуживает проверенный готовый пакет при настройке каталога
артефактов; см. [памятку](../backend/handoff/README.md). Датированный результат
публичного B2 и Docker AMD64 — в [протоколе 27 сентября](submission-final/docker-inference-verification.md); свежая сверка ready/capabilities — в итоговой приёмке.

После локального запуска или `docker compose up --build` ту же smoke-проверку связи можно выполнить из корня:

```sh
.venv/bin/python -m scripts.check_integration --base-url http://127.0.0.1:5173
```

Она проверяет HTML, health и прогноз через прокси, но не отрисовку в браузере.
Успех относится только к синтетическому контуру. Для реального прогноза в
[паспорте модели](../ml/reports/model-card.md) указаны время CLI batch и размер артефакта;
HTTP p95/RPS и ресурсы локального handoff измерены отдельно в
[протоколе нагрузки](verification-load.md); цифры не относятся к VPS.

## Сервер и производительность

**Ресурсы всего VPS, а не минимальные требования приложения.** Параметры тарифа
по описанию, предоставленному Даниэлем 25 сентября 2026 года:

| Параметр | Значение по тарифу |
|---|---|
| CPU | 4 CPU |
| Оперативная память | 8 ГБ RAM |
| Процессорная платформа | AMD EPYC до 3,5 ГГц или Intel Xeon Scalable до 3,2 ГГц; конкретная модель на VPS пока не проверена |
| Накопитель | SSD, диапазон в описании тарифа — 80–120 ГБ |

Это сведения о тарифе, а не результат аппаратной проверки сервера. Схема развёртывания:
backend в Docker, Caddy и собранный frontend на хосте; инструкции — в [deploy/README.md](../deploy/README.md).
В текущем `compose.server.yaml` лимиты CPU/RAM контейнера не заданы.

В отдельном [протоколе проверки GitHub/VPS](reproducibility-audit-2026-09-25.md)
зафиксированы 4 CPU, около 7,7 GiB RAM и корневой раздел 79 GiB. Там же указан
серверный checkout `bdf2a32`: он отстаёт от main, handoff/ready на VPS возвращал
404. Это датированный результат другой проверки, не повторный замер этого
аудита и не нагрузочный тест; актуальное состояние сверять перед развёртыванием.

Позднее 25.09.2026 VPS обновлён до кода `88144ef` и получил реальный ML-пакет.
API, UI, CSV и сохранение release при повторном обновлении проверены:
[протокол деплоя](verification-deployment-2026-09-25.md).

Для handoff-развёртывания нужны `compose.server.yaml` и `compose.handoff.yaml`
с `TRAMFLOW_HANDOFF_HOST_DIR`. Текущий updater сохраняет mount и у остановленного
backend; для первой установки или смены release путь задаётся явно.
Синхронизация исходников, установка пакета и приёмка описаны в
[серверной инструкции](../deploy/release.md). После слияния PR обновление VPS
выполняется отдельно; `git pull` сам не пересобирает сервисы.
Опциональный Basic Auth подготовлен отдельно; его наличие в Git не означает
включение на VPS. Настройка и проверки — [deploy/access.md](../deploy/access.md).

Локальная выдача через Vite проверена при 2 CPU / 4 GiB / 1 worker: ступень
200 RPS × 5 минут дала 199,967 RPS, p50 1,964 мс, p95 9,310 мс,
p99 37,098 мс, ошибок 0%, semantic 100%, dropped 0.
[Полный протокол нагрузки](verification-load.md) содержит ресурсы и ограничения.
Это измерение локального Docker Desktop, не производительности VPS/Caddy.
В этом локальном профиле пороги 200 RPS, p95 <300 мс и отсутствие ошибок
достигнуты. Наблюдённый максимум backend CPU — 45,68% лимита двух CPU,
после прогона RSS 64 788 KiB и VmSwap 0. HTTP-нагрузочное подтверждение на VPS остаётся отдельным шагом. Сценарный B2 smoke (26.09, 2 CPU / 4 GiB / 1 worker, 60 с) дал 199,945 RPS, p95 16,042 мс; он относится к прежней двухфакторной версии, не к новому четырёхфакторному прогону. Точные версии и raw evidence — в [проверках](submission-final/verification.md) и итоговой приёмке.

## Короткая ветка и небольшой PR

1. Обновите основную ветку команды: `git switch main`, затем `git pull --ff-only` (если основная ветка называется иначе, используйте её имя).
2. Создайте ветку для одной задачи: `git switch -c feature/forecast-loading`.
3. Сделайте небольшое законченное изменение и проверьте его:

   ```sh
   .venv/bin/python -m unittest discover -s tests/integration -v
   npm run build --prefix frontend
   docker compose config --quiet
   ```

4. Для изменений UI откройте страницу; остановите backend, нажмите «Повторить запрос» и проверьте понятную ошибку. После запуска backend повторный запрос должен восстановить график.
5. При изменении интерфейса, формата, конфигурации или запуска обновите свой раздел `INTEGRATION.md` **в том же PR**. Несовместимое изменение сначала согласуйте с владельцем принимающей части.
6. Просмотрите `git diff` и `git status`, исключите реальные данные и секреты. Сделайте commit, отправьте свою ветку и откройте небольшой PR по шаблону. Попросите проверить владельца затронутой части.

Команды commit/push участник выполняет сам; подготовка заготовки их не выполняет.
