## 7. Архитектура, производительность и поставка

Разделение batch ML → проверенный immutable handoff → API → UI разумно для исторического горизонта. `backend/handoff/store.py:81` проверяет manifest/хеши/схему/единицы/дубликаты; `api.py:136` использует точное суммирование и coverage. Есть ограничения размеров, ошибки 409/410, read-only mount. Это выдача готового прогноза, не обучение и не model inference на каждый HTTP-запрос.

[Нагрузочный протокол](../../verification-load.md) сверён с raw JSON/logs: 60 001 измеренный запрос, **199,967 RPS**, **p95 9,310 мс**, p99 37,098 мс, ошибок и dropped 0, semantic 100%. Один backend worker, 2 CPU / 4 GiB, локальный Docker; максимум CPU 91,36% одного CPU = 45,68% лимита двух CPU, VmSwap 0. Большой экспорт 7440 строк — один замер 889,049 мс, не p95. Два пересоздания сохранили mount/run. Это не измерение VPS, браузерной отрисовки, одновременного большого экспорта или ML inference.

Нагрузочно значимые backend/load-файлы не изменились относительно проверенной базы. Принцип масштабирования одинаковых read-only пакетов описан, но запуск двух реплик не доказан. Нет основания заново ставить обязательную задачу «измерить первые 200 RPS» или переписывать FastAPI на Java. Повтор нужен при изменении обслуживаемого расчёта/ресурсов, например после сценарного API.
