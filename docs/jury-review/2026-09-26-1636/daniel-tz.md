## D1 · P1 · Ручные сценарные коэффициенты: сквозной +1 K2

**Критерий:** отдельный пункт K2 PDF4 — пользователь меняет поправку и сразу видит прогноз. **Проблема:** публичный capabilities сообщает `scenario_supported=false`, UI коэффициентов нет. **Владелец:** Даниэль; реализация по согласованию Толя ↔ Артём; Игорь проверяет понятность единиц; Георгий подтверждает, что это ручная поправка, а не переобучение. **Принимающие:** Даниэль, Толя и Артём на одном сквозном примере.

**Входы/области:** действующий base query/export, `backend/handoff/api.py`, `frontend/src/{handoff,useForecast}.ts`, `components/{FilterBar,ForecastCard,DataDetails,AnalyticsView,Workspace}.tsx` — фактические имена компонентов сверить перед изменением. Новую сценарную логику выделить отдельно. Float base, DS CSV, schema `ml-handoff-v1` и существующие ошибки сохраняются.

**Предлагаемое поведение:** панель «Сценарий» с двумя подписанными ручными поправками «Погода» и «Событие», нейтрально 1,00; источник — «допущение диспетчера». База, сценарий и разница видны вместе; кнопка сброса. Для минимальной версии коэффициенты постоянны на выбранном периоде. Сезонную поправку добавлять только если не усложняет приёмку; количество ползунков не даёт дополнительных баллов.

**Проект расчёта и API, требуется согласование:**

- `scenario_value = base_value × k_weather × k_event`. Предлагаемый диапазон каждого 0,5–1,5 с шагом 0,05; это продуктовый выбор команды, не норма организаторов. Отказ при NaN/∞/отрицательных/вне диапазона. Нет скрытой отсечки суммарного результата.
- Неподдержанные данные сохраняют `null`; coverage/status не улучшаются от умножения. № 5 остаётся 0 и baseline, предупреждение сохраняется.
- Один backend расчёт обслуживает UI и экспорт. Предлагаются отдельные `/api/v2/scenarios/query` и `/api/v2/scenarios/export` с текущими filters/run и коэффициентами; имена и схема пока не реализованы. Действующий `/api/v2/handoff/*` продолжает отдавать базу без изменения семантики.
- Сценарный результат хранит ссылку на base result, версию алгоритма, коэффициенты, единицы и своё ID, зависящее от run, filters и коэффициентов. Экспорт закреплён за этим ID. CSV явно содержит base/scenario/delta и коэффициенты; это не конкурсный файл.
- Базовый интервал неопределённости не объявлять откалиброванным сценарным интервалом. Минимум: показывать его только для базы, у сценария — «интервал не оценён». Механическое умножение границ без этой оговорки не принимать.

**Сквозной пример:** выбран route/time, в реальном base API значение 100. Пользователь задаёт 1,10 и 1,20 → backend 132, delta +32; UI карточка/график/таблица показывают тот же результат, scenario CSV содержит 100/132/+32 и коэффициенты. Сброс 1/1 возвращает ровно 100. На production-данных ожидаемое значение брать из base ответа, не подменять пакет учебной сотней.

**Действия и проверки:** сначала согласовать пример/схему и лимиты; backend реализация с тестами формулы, null, baseline, несовпадения ID; frontend с отменой старых запросов и блокировкой устаревшего экспорта; UI-сценарий день/месяц, быстрые смены коэффициентов, reset, смена route/date; сверка CSV с ответом. Если расчёт добавлен в измеряемый запрос, обновить локальную проверку производительности; старый load не выдавать за новый.

**Приёмка:** коэффициент меняет числа без перезагрузки страницы; base сохранён; все представления одинаковы; значение 132 проходит пример; нет ответа старого фильтра поверх нового; null не превращается в 0; DS не изменился. Обновлены capabilities/документация в согласованной форме, в `INTEGRATION.md` функция отмечена работающей только после проверки. **Выход:** согласованный контракт, реализация, протокол со сквозными числами/CSV.

**Время:** 2–4 ч, первый результат в следующие 6 ч, принят до freeze. **Stop/fallback:** если к концу окна нет согласованного backend/export, не показывать «работающие сценарии» с чисто декоративным ползунком; сохранить base и признать незакрытый балл. Сократить число коэффициентов, а не целостность расчёта.

**Готовое сообщение:**

## D3 · P1 · Сводка спроса и законченное действие диспетчера

**Критерии:** K4 карта/временная динамика; K5 польза. Вместе с D2 ожидается +1–2 K4 и до +1 K5, не отдельный балл за каждый элемент. **Проблема:** «Все маршруты» сейчас очищает выбор; `Workspace.tsx:104–109` не передаёт временной спрос в карту; аналитика лишь расширяет тот же ряд. **Владелец:** Даниэль; запрос Артёму на UI, Толе на использование multi-route API, Игорю на правила сравнения; принимают Даниэль/Игорь.

**Входы/области:** актуальный capabilities, уже работающий multi-route `handoff/query`, `Workspace.tsx`, `AnalyticsView.tsx`, компонент карты, `useForecast.ts`. Сохранять чужие изменения геометрии/подписей; этот пункт не поручает очередную перерисовку схемы. Согласовать API-потребление с Толей, не увеличивать молча лимиты.

**Действия:**

1. Сделать явный «Обзор маршрутов» для всех routes из capabilities. Один запрос на общий период/resolution; не гонять 10 одинаковых цепочек. Для дня 10×24=240 строк, для месяца daily ≤310, оба режима внутри текущих лимитов.
2. Таблица: маршрут, успешные посадки за период, время максимума, coverage, статус. № 5 в отдельной категории baseline; partial/no_data не сравнивать как полный нулевой спрос. Сортировка по сумме или значению выбранного интервала подписана как спрос, не перегрузка. При равенстве — стабильный порядок номера; никакого непрозрачного «AI риска».
3. Выбор строки ведёт в существующую карточку/маршрут на карте, сохраняет дату. Смена временной точки меняет подписанное значение на схеме для выбранного маршрута. Минимум — маршрутный badge/панель рядом со схемой плюс читаемая легенда и изменение индикатора; для полной карты спроса — сопоставимые значения/цвета маршрутов с фиксированной шкалой на период. Цвет/толщину согласовать с Артёмом, не потерять различимость линий.
4. Обязательно подписать: значения на уровне маршрута; схема 2026, прогноз 2025; остановочная распределённость не оценена. Не размножать route total в «нагрузку каждой остановки». Не интерполировать физические координаты из пикселей PDF.
5. Дать блок «Следующее действие»: сравнить выбранный период с соседними часами/днями, проверить фактический выпуск/интервалы, при наличии данных оценить перераспределение. Показывать числа сравнения и допущения; не выдавать автоматическое «добавить N вагонов» без данных. При включённом D1 явно выбирать слой «База»/«Сценарий» и показывать применённые коэффициенты; не смешивать сценарные значения одного маршрута с неподписанной базой остальных.

**Пример:** в обзоре выбран один день и час; маршрут A=1000, B=500 успешных посадок, coverage обоих 100%. A находится выше B по спросу, но не подписан «переполнен». Клик A показывает тот же час и число в карточке/таблице/индикаторе; следующий час A=600 обновляет все три. Экспорт соответствует явно указанной области: весь обзор или выбранный маршрут, а не случайный старый фильтр. Это учебные числа для теста, не замена реальных прогнозов.

**Приёмка:** сводные суммы совпадают с API; выбранное время/маршрут едины; нет сетевого каскада на каждый tick анимации; № 5/no_data не скрывают проблему качества; одинаковые числа в таблице/карте/экспорте; период виден; пользователь за ≤3 основных действия от обзора получает конкретный маршрут и период для проверки. Сравнение корректно по одинаковым единицам и длине интервала. На мобильном доступна таблица/карточка, даже если карта свёрнута. **Выход:** сквозной демо-сценарий, численный протокол, принятые UI/документы.

**Время:** 3–5 ч, минимальный проход в следующие 6 ч, итог до freeze. **Stop/fallback:** при риске для геометрии оставить существующую карту, сделать сводную таблицу и динамический badge выбранного маршрута; не заявлять полноценную остановочную heatmap. Если ранжирование не готово, не называть пустой выбор «обзором» — переименовать его в «Снять выбор» и явно оставить D3 частично выполненным.

**Готовое сообщение:**

## D5 · P2 · Подтвердить горизонтальное масштабирование, если есть резерв

**Готовое сообщение:**
