# BE-01: пакет согласования HTTP v2

Версия `2.0-draft.1`, 25 сентября 2026. **Предложение Толи, не принятый контракт.**
Это работающий генератор схем и проверяемые примеры, а не реализация API v2.
Новые HTTP-маршруты в `backend.main:app` не зарегистрированы; v1 и ML не изменены.
BE-01 нельзя считать завершённым до подтверждения принимающих участников.

## Что передать на проверку

- `generated/openapi-v2-draft.json`: все шесть операций из общего ТЗ.
- `generated/examples-v2-draft.json`: query/export, success, empty, partial,
  stale, scenario, qualitative, ошибки и служебные ответы.
- `v2.py`: источник Pydantic-схем; `openapi.py`: генерация OpenAPI.
- Этот документ: семантика и отличия, требующие принятия.

Все ID и числа демонстрационные. `synthetic_count`/`synthetic_units` не являются
названиями показателя организаторов. `result_id` в примерах иллюстративный,
его вычисление пока не реализовано. Геометрия отсутствует намеренно: непроверенные
координаты и привязки к существующей художественной карте не добавляются.
Fixtures не доказывают качество ML, реальные ограничения хранения или производительность.

Источник требований: персональное ТЗ BE-01..08, `docs/team-specs/shared-contract.md`,
`docs/integration/contract-review.md`, PDF организаторов (6 страниц): REST и
агрегация/экспорт — стр. 1–2, производительность — стр. 3 и 5, коэффициенты — стр. 4.
Java/Spring — рекомендация; FastAPI сохраняется. Неоднозначность месяца/года
на стр. 1/2/5 остаётся вопросом организаторам. Упоминание потоковых данных не
задаёт протокол приёма. Организаторский DS CSV и пользовательский экспорт различаются.

## Воспроизведение

Из корня, после установки `backend/requirements.txt`:

```sh
.venv/bin/python -m backend.contracts.openapi
.venv/bin/python -m backend.contracts.openapi --check
.venv/bin/python -m unittest discover -s backend/tests -v
.venv/bin/python -m unittest discover -s tests/integration -v
```

Генератор не запускает сервер, не читает данные и не вызывает ML. `--check`
проверяет соответствие JSON исходникам без записи. Эти команды добавлены в CI
перед существующими интеграционными проверками. Публикация не выполнялась.

OpenAPI описывает структурную проверку. Межполевые Pydantic-валидаторы
не полностью выражаются в JSON Schema: например, порядок дат, произведение
коэффициентов и согласованность фильтров ответа. Примеры и правила ниже
нужно передавать вместе со схемой, даже если TypeScript-типы генерируются автоматически.

## Решения на согласование

Существующий журнал CR-01..08 остаётся у Даниэля. Таблица ниже — предложения,
а не отметки чужого подтверждения. Физический manifest и Python ML-интерфейс
этим пакетом не определяются.

| Решение | Предложение в draft.1 | Кто принимает |
|---|---|---|
| CR-01 | `metric_id`/`unit` — непустые строки; действительные значения и аддитивность приходят из паспорта. Суммирование пока не реализовано | Игорь, Георгий, Даниэль, Артём |
| CR-02 | Версии в HTTP не определяют структуру файлов. Backend получает готовый run, модель загружается в batch-контуре | Георгий, Игорь, Даниэль |
| CR-03 | `as_of` берётся из run; произвольного as_of в query нет | Георгий, Артём, Даниэль |
| CR-04 | Зафиксировать snapshot фактов вместе с run; добавить `facts_version` и `calculation_version`. Факты в ответе относятся к этому snapshot, а не к текущему времени HTTP | Игорь, Артём, Даниэль |
| CR-05 | Export требует новый `expected_result_id`; при несовпадении — новый 409 `result_mismatch`. Query возвращает фильтры с закреплённым run | Артём, Игорь, Даниэль |
| CR-06 | `summary.total_scope` явно различает полный итог, доступную часть и неприменимость; no_service — подтверждённые нули. `priority` пока null/normal/attention, правила расчёта ещё не определены | Георгий, Игорь, Артём |
| CR-07 | Ready имеет отдельный диагностический ответ и на 503; `real_ready=false` для synthetic. Capabilities показывает реальные сочетания и retention в секундах; значение 0 в fixture не обещает хранение 24 часа | Игорь, Артём, Даниэль |
| CR-08 | Формы network/capabilities/quality, ошибок и nullable полей из OpenAPI должны быть приняты до подключения UI | Артём, Георгий, Игорь, Даниэль |

Дополнительные уточнения проекта HTTP, требующие принятия:

- `start/end` задают **срез** внутри горизонта; не обязательно все 24 часа/30 дней.
  В fixture четыре часа: `[09:00,13:00)`. Границы выравниваются в МСК; эквивалентные
  ISO-времена в UTC допустимы. Ограничения 24 часа/30 дней/12 календарных месяцев
  проверяются в схемах; поддержанные комбинации и наличие данных проверит query.
  Это уточнение отношения горизонта и выбранного интервала, не решение организаторов.
- `scenario` передаёт числовые коэффициенты, не строки. Нейтральное значение 1,
  шаг 0.05, диапазон каждого 0.5–1.5, произведения 0.5–2.0. Выход отклоняется.
  Расчёт сценария BE-06 ещё не реализован. Базовые доверительные интервалы
  в сценарном ответе не допускаются как калиброванные.
- Неизвестные поля отклоняются, чтобы опечатка в фильтре не расширяла выборку.
  Наличие ID в справочниках, расписание для no_service, отсутствие дублей,
  аддитивность и знаменатель coverage проверит слой данных/query, не wire-схема.
- Coverage относится к ожидаемым базовым ячейкам. Пустой срез: null и total=null;
  qualitative с ожидаемыми, но нечисловыми ячейками: 0 и total=null.
  Смешанный model/baseline: row.method сохраняется; определение верхнего mode
  остаётся открытым и не подменяется придуманным правилом.
- Network предлагается как GeoJSON FeatureCollection с проверенными ID,
  необязательной геометрией и network_version; порядок остановок — sequence.
  Пиксели PDF не преобразуются в геокоординаты. Для остановки, общей нескольким
  маршрутам/направлениям, связи задаются отдельными features; проверить с Игорем.
- `lower/upper` требуют `interval_method` и `interval_coverage` — дополнительные
  поля для выполнения требования обоснованных интервалов. Агрегированные
  интервалы нельзя получать простым сложением квантилей.
- Details ошибки — список безопасных code/message; traceback, пути и исходные
  строки данных не включаются. Текущий runtime-обработчик 422 не меняется: v2
  ещё не подключён. При реализации нужен отдельный обработчик для envelope v2.

## Предлагаемый result_id (CR-04/05; пока не реализован)

Нормализовать времена в UTC, упорядочить и удалить повторы route_ids/entity_ids,
развернуть defaults; scenario=null и нейтральные коэффициенты привести к одному
представлению, коэффициенты фиксировать с двумя десятичными знаками.
Включить все фильтры, schema_version, run, версии модели/данных/сети/фактов/расчётов
в канонический JSON с фиксированным порядком ключей, затем SHA-256.
request_id и текущее время обращения в хеш не включать. Изменение правила
канонизации требует новой calculation_version. На экспорт пришедший ожидаемый
result_id сравнивать с пересчитанным; истёкший run — 410, несовпадение — 409.
Вопрос limits: считать 100 маршрутов до или после дедупликации. В draft.1
структурный предел применяется до неё; запрос сверх него получает 422.
Оценка числа строк и лимит памяти позднее дают 413 до дорогого расчёта/выдачи.

## Исправления после самопроверки перед отправкой

В рамках BE-01 усилена проверка уже описанного draft без добавления полей
и без подключения к runtime. Общий контракт требует ISO-время с зоной,
временную сетку выбранного шага и отсутствие численного качественного прогноза.
Эти исправления не меняют интерфейсы ML/frontend и не означают принятие v2.

- Все временные поля, включая generated_at/as_of/data_cutoff, используют
  ISO-парсер с обязательной зоной. Числа и строки с Unix timestamp отклоняются;
  ISO-время с UTC/смещением и Python datetime с зоной сохраняют поддержку.
- Верхний mode=qualitative требует качественных строк, без численного total,
  peak_value и положительного численного покрытия. actual_value/reference_value
  могут содержать исторические сравнения; это не прогнозные числа.
- Каждая строка ответа занимает один интервал resolution и выровнена в МСК:
  час, календарный день либо календарный месяц. Поддержаны эквивалентные UTC-границы,
  високосный февраль и переход декабря в январь. Пропуски не заполняются нулями.

Добавленные регрессионные тесты воспроизвели ошибки до исправления. После
исправления проверяются 29 контрактных тестов; это проверки формата и согласованности,
не доказательство корректности будущего алгоритма агрегации. Сохранённые OpenAPI
и примеры остаются актуальны: межполевые ограничения выполняются в Pydantic.
